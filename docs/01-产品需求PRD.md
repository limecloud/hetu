# 产品需求 PRD

版本：V1.0；日期：2026-11-13。产品范围、功能需求与发布判据以本章为准。

## 1. 产品定义

河图 Hetu 是面向小说作者、编剧与小型工作室的本地多作品创作工作台。作者书库管理多部独立小说，每部作品拥有自己的封面、简介、分卷章节、大纲、设定集、素材与版本。改编短剧以独立项目维护分集、场次和剧本，并明确关联原著及固定来源。系统负责存储、结构化、约束校验、审核、版本与交付；系列或共同世界观由作者按需建立关联。

标语：**设定有据，创作有序**。工作原则：设定集先行，作者掌规，Agent 佐笔。

桌面端默认进入作者自己的写作流程：选书、整理卷章、按照个人风格撰写和修改、保存及定稿。编辑体验以作者正文为中心，作者可以全程自主创作，也可以在需要时寻求外部 AI 帮助；同一作品、同一章节可交替使用两种方式，无需选择固定的创作模式。

AI 协作围绕具体任务设计。作者按需选择客户端、安装对应扩展、复制任务提示词，在 Codex、WorkBuddy、Claude Code 等外部客户端与 AI 对话。软件负责准备上下文、展示成果、作者编辑和验收，不实现 AI Agent、聊天或自动生成循环，不内置模型或生成 API。AI 改稿作为独立参考版本返回；作者可只阅读、自行重写、选择部分采纳或放弃全部建议。采纳须预览并明确确认，定稿单独决定。关闭 MCP、断网、没有第三方账号时，创作、抽取、规则校验、本地批注、本地 Git 与导出仍可独立完成。

## 2. 问题、用户与价值

| 用户 | 当前任务与痛点 | 河图提供的结果 |
| --- | --- | --- |
| 小说作者 | 多部作品的封面、卷章、设定与进度散落 | 作者书库、独立作品资料、可引用设定集与证据诊断 |
| 改编编剧 | 小说段落难以转换成可讨论的场次 | 有原文映射、缺失项和冲突提示的分集骨架 |
| IP 工作室 | 素材、草稿与定稿混用，交付版本难追溯 | 审核状态、固定版本及有摘要的交付包 |
| Agent 使用者 | 每轮重复提供人设，生成结果难以约束 | 可发现的设定集、草稿工具、校验反馈与权限边界 |

首要用户群体为中国的中文创作者与 IP 工作室，同时支持英文创作及跨语言协作。产品以真实章节维护、改编和交付任务的耗时、误报、返工与作者反馈评价体验。

## 3. 产品红线

| 负责 | 不纳入核心 |
| --- | --- |
| 设定集、规则、内容、版本与审核 | 内置 LLM、嵌入式聊天 Agent、模型账号托管 |
| 从已有文本抽取带来源的结构与候选 | 自动续写、自动编对白、补充没有来源的情节 |
| 将确认节点排列成结构骨架 | 自动拍摄方案、自动生成镜头与成片 |
| 线索与既有媒体文件的存储、溯源 | 核心直接调用第三方生成接口 |
| 可选插件的导入、结果审核合同 | 核心代收算力费、保证供应商版权或稳定性 |

可选商业插件独立发布、显式启用；其网络与费用行为不进入默认开源安装。具体边界见[22](22-插件生态开源许可与商业化.md)。

桌面创作与随软件提供的本机 MCP 是首要交付范围；官网提供宣传、使用指南及发行入口。服务端业务须由明确的作者需求单独立项，不作为 V1 本机功能的前置。职责与实施顺序见[03第8节](03-总体技术架构.md#8-桌面端与-web-服务端职责)和[20第5节](20-实施路线与里程碑.md#5-服务端演进与准入顺序)。

## 5. 用户主流程

1. 打开作者书库，可直接手工作业，或在“AI 协作”中选择客户端并按引导安装对应扩展。
2. 创建小说时可先录入已有资料，也可把一个想法交给专用 Skill。复制 Prompt 后在外部客户端对话，回河图比较书名、简介和大纲候选；作者确认资料及目录后创建作品。
3. 作者维护设定集、分卷与章节，直接在编辑器按自己的风格写作和改稿。需要 AI 协助时，再选择本次原文范围、修改目标、希望保留的表达与上下文，复制提示词；完整对话、模型和生成均在外部 Agent。
4. 通过 MCP 或固定 inbox 接收独立参考成果。MCP Apps 可提供局部选择和预览，必要时用本地网页配合；不支持增强交互时回到原生界面。收到参考稿不改变作者正文。
5. 作者可只将候选作为参考自行撰写，也可预览后明确采纳整稿或所选片段，继续编辑；候选来源与实际采纳记录保留。无需使用参考内容即可继续写作和定稿。
6. 对已有章节抽取并校正节点、整理短剧骨架，手工或通过外部 Skill 起草剧本；设定建议由作者单独确认。
7. 作者对选定的已保存写作稿执行检查并独立确认定稿。定稿绑定确切修订，后续编辑形成新写作稿，旧定稿保留。
8. 可选提交 Git 快照、推送指定远端；导出固定输入版本的 IP Bundle。软件不自动向阅读或投稿平台发稿。

封面可直接导入，或由河图提供与所选客户端适配的 Prompt、作者在外部 Agent 调用配套 Skill 后写回候选目录，再回到河图选用，详见[34](34-小说封面与Agent协作.md)。建书前可以探索封面方向，正式选用需绑定已创建作品。封面设计与其他小说的设定、正文、审核和版本独立。

Git、远端与 Agent 均不是导出的前置条件。纯手工路径不能因没有 Agent 而中断。完整分支与时序见[23](23-业务流程与MCP时序.md)。

## 6. 非功能需求

- 本地优先：核心任务离线；默认不收集正文、遥测或自动上传。
- 数据可持有：UTF-8 Markdown／Fountain／JSON 与普通媒体文件，不依赖私有数据库才能读取原文。
- 无静默覆盖：并发写入、外部修改和过期审核采用版本与摘要检查。
- 可解释：每个问题具有规则、来源、级别、覆盖及证据，不用一个分数代替结论。
- 可恢复：崩溃保留已保存版本与未完成操作，恢复不重新执行未知推送。
- 跨端一致：业务、Schema、错误、状态与测试夹具共享；文件权限、编辑器与凭据分别原生适配。
- 国际化：zh-CN 为默认语言、en 为完整支持语言，机器字段稳定，内容、界面与交付语言独立，见[31](31-国际化与中文体验.md)。
- 性能与规模按明确硬件、测量方式和门槛验收，见[19](19-测试策略与验收矩阵.md)。

## 7. 发布与成功判据

V1 发布需全部 P0 需求的正向、失败与恢复验收通过，FR-17 独立评估。两端分别验收自主写作至定稿交付的完整旅程，以及作者按需发起外部协作、比较参考稿、选择性采纳和继续编辑的旅程；还须证明 Agent 无法通过受管 API 修改作者正文、设定集、定稿或选用正式封面。Apps 至少在一个明确版本的支持宿主通过；其他所声明客户端的无 Apps 路径也必须通过。本地网页单独验收，不能用它代替原生编辑器。

小说和剧本采用明确的内部源格式、转换报告与交付 profile；文件标准、行业惯例、制片方模板分别标注。格式范围与规范依据见[25](25-小说与剧本标准格式.md)，不将自定义 JSON 或中文短剧模板称为通行行业标准。

试点记录候选采纳率、确定规则误报、诊断覆盖、数据恢复成功与任务耗时；不得用测试集通过率宣传为所有小说的语义准确率。发布必须同时满足许可证、固定工具链、宿主兼容与签名要求。

## 8. 架构选型背景与设计目标

河图需要长期管理本地目录、正文和媒体、设定集修订、Git 冲突、复杂审核及可交付版本。选择原生工作台与独立 native MCP，是为了让这些任务共用可验证的业务、文件事务和恢复底座；Codex 插件承担方法与连接，MCP Apps 承担聚焦的人类检查。

原生路线统一文件身份、事务恢复、系统凭据与长文交互；Codex 插件和 MCP Apps 通过受限接口复用这些能力。技术理由与代价见[02](02-架构选型与设计原则.md)。

设计目标是正典与生成解耦、内容独立于模型上下文、核心离线、受管入口校验、作者最终决定、版本可追溯及标准格式交付。生成供应商可选，核心仍承担自身依赖、数据完整性与安全责任；设定集锁不替代 OS 或团队权限。

## 9. 技术架构摘要

共享 Rust 内核负责领域、规则、存储、libgit2 与交付；稳定 C ABI 供 SwiftUI/AppKit、WinUI 3 和统一 Swift CLI 调用。本地 Rust MCP Server 为外部 Agent 提供标准工具与资源，协议采用范围按官方版本和宿主证据冻结。源码采用一个 Monorepo，作者内容工作区独立存放。

IP 正典和文本使用可读 JSON／Markdown／Fountain，索引可用可重建数据库；业务事实不依赖某个模型对话。插件、MCP、AXI 和 UI 资源各有版本和职责，联合设计见[27](27-Agent与Codex插件集成设计.md)，完整架构见[03](03-总体技术架构.md)。
