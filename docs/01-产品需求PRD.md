# 产品需求 PRD

版本：V1.0；日期：2026-11-12。产品范围、功能需求与发布判据以本章为准。

## 1. 产品定义

河图 Hetu 是面向网文作者、编剧与小型 IP 工作室的本地 IP 工程化工作台。作者建立、维护并锁定设定，以同一套角色、势力、地点、时间线和世界规则组织小说及衍生工程。系统负责存储、结构化、约束校验、审核、版本与交付。

标语：**设定有据，创作有序**。工作原则：设定集先行，作者掌规，Agent 佐笔。

核心不内置模型，不提供文本、图片、音乐、视频生成 API。Codex、WorkBuddy 等外部 Agent 在各自产品内生成内容，使用河图 MCP 提交受约束的草稿。关闭 MCP、断网、没有第三方账号时，手工创作、抽取、规则校验、审核、本地 Git 与导出仍可独立完成。

## 2. 问题、用户与价值

| 用户 | 当前任务与痛点 | 河图提供的结果 |
| --- | --- | --- |
| 长篇网文作者 | 角色身份、时间与世界规则散落，人设维护成本高 | 可引用的设定集与能跳回证据的诊断 |
| 改编编剧 | 小说段落难以转换成可讨论的场次 | 有原文映射、缺失项和冲突提示的分集骨架 |
| IP 工作室 | 素材、草稿与定稿混用，交付版本难追溯 | 审核状态、固定版本及有摘要的交付包 |
| Agent 使用者 | 每轮重复提供人设，生成结果难以约束 | 可发现的设定集、草稿工具、校验反馈与权限边界 |

首要用户群体为中国的中文创作者与 IP 工作室，同时支持英文创作及跨语言协作。产品以真实章节维护、改编和交付任务的耗时、误报、返工与作者反馈评价体验。

## 3. 产品红线

| 负责 | 不纳入核心 |
| --- | --- |
| 设定集、规则、内容、版本与审核 | 内置 LLM、嵌入式聊天 Agent、模型账号托管 |
| 从已有文本抽取带来源的结构与候选 | 自动续写、自动编对白、补充没有来源的情节 |
| 将确认节点排列成结构骨架 | 自动拍摄方案、自动生成镜头与成片 |
| 线索与既有媒体文件的存储、溯源 | 核心直接调用第三方生成接口 |
| 可选插件的导入、结果审核合同 | 核心代收算力费、保证供应商版权或稳定性 |

可选商业插件独立发布、显式启用；其网络与费用行为不进入默认开源安装。具体边界见[22](22-插件生态开源许可与商业化.md)。

## 5. 用户主流程

1. 选择新目录创建 IP 工作区，或通过系统选择器打开已有工作区。
2. 建立设定集并写作；可选授权外部 Agent 读取选定设定集、提交草稿。
3. 查看人物与场景候选，选择已有实体或由作者新增，确认后锁定设定。
4. 对选定已有章节抽取节点，校正人物、时间、场景与因果线索。
5. 按集长和分场目标整理骨架；手工或外部 Agent 填充剧本草稿。
6. 校验并处理确定冲突、启发式提示和未覆盖项，再由作者审核定稿。
7. 可选提交 Git 快照、推送指定远端；导出固定输入版本的 IP Bundle。

Git、远端与 Agent 均不是导出的前置条件。纯手工路径不能因没有 Agent 而中断。完整分支与时序见[23](23-业务流程与MCP时序.md)。

## 6. 非功能需求

- 本地优先：核心任务离线；默认不收集正文、遥测或自动上传。
- 数据可持有：UTF-8 Markdown／Fountain／JSON 与普通媒体文件，不依赖私有数据库才能读取原文。
- 无静默覆盖：并发写入、外部修改和过期审核采用版本与摘要检查。
- 可解释：每个问题具有规则、来源、级别、覆盖及证据，不用一个分数代替结论。
- 可恢复：崩溃保留已保存版本与未完成操作，恢复不重新执行未知推送。
- 跨端一致：业务、Schema、错误、状态与测试夹具共享；文件权限、编辑器与凭据分别原生适配。
- 国际化：zh-CN 为默认语言、en 为完整支持语言，机器字段稳定，内容、界面与交付语言独立，见[31](31-国际化与中文体验.md)。
- 性能与规模按明确硬件、测量方式和门槛验收，见[19](19-测试策略与验收矩阵.md)。

## 7. 发布与成功判据

V1 发布需 FR-01～FR-13、FR-15、FR-16、FR-18、FR-19 的正向、失败与恢复验收通过；FR-14、FR-17 不作为发布前提。两端分别完成从建项目、写作、抽取、改编、审核、版本到离线导出的完整旅程，并证明 Agent 无法通过受管 API 修改设定集或自批草稿。

小说和剧本采用明确的内部源格式、转换报告与交付 profile；文件标准、行业惯例、制片方模板分别标注。格式范围与规范依据见[25](25-小说与剧本标准格式.md)，不将自定义 JSON 或中文短剧模板称为通行行业标准。

试点记录候选采纳率、确定规则误报、诊断覆盖、数据恢复成功与任务耗时；不得用测试集通过率宣传为所有小说的语义准确率。发布必须同时满足许可证、固定工具链、宿主兼容与签名要求。

## 8. 架构选型背景与设计目标

河图需要长期管理本地目录、正文和媒体、设定集修订、Git 冲突、复杂审核及可交付版本。选择原生工作台与独立 native MCP，是为了让这些任务共用可验证的业务、文件事务和恢复底座；Codex 插件承担方法与连接，MCP Apps 承担聚焦的人类检查。

原生路线统一文件身份、事务恢复、系统凭据与长文交互；Codex 插件和 MCP Apps 通过受限接口复用这些能力。技术理由与代价见[02](02-架构选型与设计原则.md)。

设计目标是正典与生成解耦、内容独立于模型上下文、核心离线、受管入口校验、作者最终决定、版本可追溯及标准格式交付。生成供应商可选，核心仍承担自身依赖、数据完整性与安全责任；设定集锁不替代 OS 或团队权限。

## 9. 技术架构摘要

共享 C++20 内核负责领域、规则、存储、libgit2 与交付；稳定 C ABI 供 SwiftUI/AppKit、WinUI 3 和统一 Swift CLI 调用。本地 C++ MCP Server 为外部 Agent 提供标准工具与资源，协议采用范围按官方版本和宿主证据冻结。源码采用一个 Monorepo，作者内容工作区独立存放。

IP 正典和文本使用可读 JSON／Markdown／Fountain，索引可用可重建数据库；业务事实不依赖某个模型对话。插件、MCP、AXI 和 UI 资源各有版本和职责，联合设计见[27](27-Agent与Codex插件集成设计.md)，完整架构见[03](03-总体技术架构.md)。
