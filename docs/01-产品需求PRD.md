# 产品需求 PRD

版本：V1.0；日期：2026-11-14。产品范围、功能需求与发布判据以本章为准。

## 1. 产品定义

河图洛书 Hetu Luoshu 是面向小说作者、编剧与小型工作室的本地多作品创作工作台。作者书库管理多部独立小说，每部作品拥有自己的封面、简介、分卷章节、大纲、设定集、素材与版本。改编短剧以独立项目维护分集、场次和剧本，并明确关联原著及固定来源。系统负责存储、结构化、约束校验、审核、版本与交付；系列或共同世界观由作者按需建立关联。

标语：**设定有据，创作有序**。工作原则：设定集先行，作者掌规，Agent 佐笔。

核心价值观：**让越来越强的 AI，围绕作者持续积累的作品工作；让每一次生成，都有机会成为可理解、可选择、可继续创作的成果。**

河图承接长期积累的作品事实、来源、修订与作者决定，外部 Agent 围绕这些材料开展工作。候选应能看清依据、比较取舍、反馈返工并接续创作；模型或会话变化后，已保存的作品与决定仍可继续使用。功能价值以作者能否掌握和延续作品衡量。

价值主张：连接小说、剧本与制作资料，帮助创作者跨过内心叙述到表演、长篇到分集、文字设定到制作连续性的鸿沟。小说与剧本工程化借鉴软件工程组织复杂工作的方式，让创作过程系统、可视、可管理，补齐资料组织和协作环节。每位作者与编剧的品味、判断、创意与独特表达都值得尊重；不提倡用AI代替这些能力，不以规则分数裁决审美。外部Agent提供候选，作者保留编辑、拒绝、取舍与定稿。证据与市场口径见[市场研究](research/12-故事改编市场与创作者价值研究.md)。

AI-first 表示外部 Agent 通过 Skills + CLI/MCP 联动整个软件，承担获权范围内的建书、资料填写、卷章与分集整理、写作参考、素材管理、检查及交付准备。桌面端的第一作用是可视化 review 与审核，帮助作者阅读、比较、理解依据、提出意见、选择采用和确认定稿；第二作用是作者亲自编辑优化。软件不充当生成代理。短剧项目管理分集计划、分集剧本、场次、制作资产及分镜，骨架是改编规划成果，不充当全部短剧内容的唯一容器。原创短剧不依赖小说存在。

默认旅程是作者向所选 Agent 表达目标，Agent 补齐必要资料并通过机器入口操作，作者在河图洛书验收成果。作者不必逐项填写表单或重复转录对话；结构化字段由 Agent 准备，界面展示结果及必要决定。所有页面提供当前对象的 AI 操作或继续提示词入口，完整覆盖见[10](10-原生客户端与交互设计.md)。手动编辑和高级手动操作独立可用，同一作品可自由交替；保存和打开正文不自动触发 AI 改稿。

Computer Use 用于界面测试验收，确无可用机器入口时才作最后兜底。建书、整理和返工若只能依靠 Agent 点击 GUI，视为接口或架构缺口，不能据此宣称 AI-first 已完成。作者决定权与执行权分开：取舍、授权和定稿仍归作者，确定性执行交给 Core；需要确认时展示具体结果和差异，不退回要求作者重新填表。

AI 协作围绕持续任务设计。作者选择客户端、一次完成本机接入，再复制当前任务提示词，在 Codex、WorkBuddy、Claude Code 等外部客户端对话。Agent 按需读取获权资料，连续维护参考稿、资料及素材候选；作者反馈后沿原任务返工，正式提交才固定候选。软件负责上下文、成果展示、作者编辑和验收，不实现 AI Agent、聊天或自动生成循环，不内置 Agent 或供应商模型。文字与图片模型工具可使用作者在本机配置的自定义渠道，或通过 hetu website 服务端接入 Cloud 开放平台；仅向外部 Agent 提供 CLI／MCP 生成封装，由作者逐计划批准固定输入外发和费用；河图作为应用在 Cloud 上架，Cloud Console 的应用入口打开河图自有控制台；页面与业务功能由 hetu website 提供，平台账号与费用能力由 Cloud 提供。AI 改稿作为独立参考版本返回；作者可只阅读、自行重写、选择部分采纳或放弃全部建议。采纳须预览并明确确认，定稿单独决定。关闭 MCP、断网、没有第三方账号时，创作、抽取、规则校验、本地批注、本地 Git 与导出仍可独立完成。

## 2. 问题、用户与价值

| 用户 | 当前任务与痛点 | 河图洛书提供的结果 |
| --- | --- | --- |
| 小说作者 | 多部作品的封面、卷章、设定与进度散落 | 作者书库、独立作品资料、可引用设定集与证据诊断 |
| 改编编剧 | 小说段落难以转换成可讨论的场次 | 有原文映射、缺失项和冲突提示的分集骨架 |
| IP 工作室 | 素材、草稿与定稿混用，交付版本难追溯 | 审核状态、固定版本及有摘要的交付包 |
| Agent 使用者 | 每轮重复提供人设，生成结果难以约束 | 可发现的设定集、草稿工具、校验反馈与权限边界 |

首要用户群体为中国的中文创作者与 IP 工作室，同时支持英文创作及跨语言协作。产品以真实章节维护、改编和交付任务的耗时、误报、返工与作者反馈评价体验。

## 3. 产品红线

| 负责 | 不纳入核心 |
| --- | --- |
| 设定集、规则、内容、版本与审核 | 内置 LLM、嵌入式聊天 Agent、模型账号托管 |
| 从已有文本抽取带来源的结构与候选 | 自动续写、自动编对白、补充没有来源的情节 |
| 将确认节点排列成结构骨架 | 自动拍摄方案、自动生成镜头与成片 |
| 线索与既有媒体文件的存储、溯源 | 核心直接调用第三方生成接口 |
| 可选插件的导入、结果审核合同 | 核心代收算力费、保证供应商版权或稳定性 |

可选商业插件独立发布、显式启用；其网络与费用行为不进入默认开源安装。具体边界见[22](22-插件生态开源许可与商业化.md)。

桌面创作与随软件提供的本机 MCP 是首要交付范围；官网提供宣传、使用指南及发行入口。服务端业务须由明确的作者需求单独立项，不作为 V1 本机功能的前置。职责与实施顺序见[03第8节](03-总体技术架构.md#8-桌面端与-web-服务端职责)和[20第5节](20-实施路线与里程碑.md#5-服务端演进与准入顺序)。

## 5. 用户主流程

先确定小说或剧本及本次目标，再区分从零、继续已有稿件或改编。来源与授权独立记录，改编不要求建立空小说；引导和导入的分支规范见[36](36-创作场景与引导流程.md)。

资料准备、剧本编写、分镜和素材设计可以分别开始，不要求作者先走完线性流水线。作者可一次授权外部 Agent 在指定项目内维护未采用资料和协作候选，设定变更、作者正文采纳、正式素材选用及定稿仍独立确认。完整资料设计见[35](35-资料素材与短剧制作资产.md)。

1. 首次从软件交接到所选外部客户端，安装和能力检查由可发现的机器入口配合完成；已有连接直接恢复。书库持续展示已保存作品与待审成果。
2. 作者给出想法或已有资料，Agent 通过专用 Skill 筹备方向、书名、简介、大纲及保存方案，填好结构化输入。作者比较成果并作必要选择后，Agent 经明确获权的新建动作创建独立作品，回读身份与目录；无需返回建书表单重填。
3. Agent 准备设定建议、分卷章节、分集计划及当前写作任务，软件展示结构、差异与待审事项。作者可以直接编辑，也可提出目标及需保留的表达，由 Agent 在固定范围内维护参考稿；完整对话、规划和生成均在外部客户端。
4. 外部 Agent 经稳定 MCP／CLI 或固定 inbox 接续原任务，先读目标、已有成果和获权上下文，保存可持续编辑的参考稿。正式提交经核验后成为固定候选，收到参考稿不改变作者正文。MCP Apps 提供局部比较和意见，较大视图可用本地网页；缺增强能力回到原生界面。
5. 作者保存公开意见后可明确“按此修改”；支持的宿主请求当前对话继续，其他情况复制继续提示词。Agent 回读原任务、具体反馈和已有稿件后返工，不因一次意见另建同义任务。缺材料时由作者确认补充范围；不复制整个聊天到作品。
6. 作者可只将候选作为参考自行撰写，也可预览后明确采纳整稿或所选片段，继续编辑；候选来源与实际采纳记录保留。无需使用参考内容即可继续写作和定稿。
7. 原创剧本可直接从人物与分集创作；小说改编按需抽取并校正节点、整理骨架，再手工或通过外部 Skill 起草剧本。设定建议由作者单独确认。
8. 作者对选定的已保存写作稿执行检查并独立确认定稿。定稿绑定确切修订，后续编辑形成新写作稿，旧定稿保留。
9. 可选提交 Git 快照、推送指定远端；导出固定输入版本的 IP Bundle。软件不自动向阅读或投稿平台发稿。

封面可直接导入，或由河图洛书提供与所选客户端适配的 Prompt、作者在外部 Agent 调用配套 Skill 后写回候选目录，再回到河图洛书选用，详见[34](34-小说封面与Agent协作.md)。建书前可以探索封面方向，正式选用需绑定已创建作品。封面设计与其他小说的设定、正文、审核和版本独立。

Git、远端与 Agent 均不是导出的前置条件。纯手工路径不能因没有 Agent 而中断。完整分支与时序见[23](23-业务流程与MCP时序.md)。

## 6. 非功能需求

- 本地优先：核心任务离线；默认不收集正文、遥测或自动上传。
- 数据可持有：UTF-8 Markdown／Fountain／JSON 与普通媒体文件，不依赖私有数据库才能读取原文。
- 无静默覆盖：并发写入、外部修改和过期审核采用版本与摘要检查。
- 可解释：每个问题具有规则、来源、级别、覆盖及证据，不用一个分数代替结论。
- 可恢复：崩溃保留已保存版本与未完成操作，恢复不重新执行未知推送。
- 跨端一致：业务、Schema、错误、状态与测试夹具共享；文件权限、编辑器与凭据分别原生适配。
- 国际化：zh-CN 为默认语言、en 为完整支持语言，机器字段稳定，内容、界面与交付语言独立，见[31](31-国际化与中文体验.md)。
- 性能与规模按明确硬件、测量方式和门槛验收，见[19](19-测试策略与验收矩阵.md)。

## 7. 发布与成功判据

V1 发布需全部 P0 需求的正向、失败与恢复验收通过，FR-17 独立评估。两端分别验收自主写作至定稿交付的完整旅程，以及作者按需发起外部协作、比较参考稿、选择性采纳和继续编辑的旅程；还须证明 Agent 无法通过受管 API 修改作者正文、设定集、定稿或选用正式封面。Apps 至少在一个明确版本的支持宿主通过；其他所声明客户端的无 Apps 路径也必须通过。本地网页单独验收，不能用它代替原生编辑器。

Mac 本期交付必须在真实 Codex 新会话中走完筹备、方向讨论、大纲资料、首章参考稿、作者反馈、返工与局部采纳，并验证恢复、原文变化、撤权、原创剧本及素材分支。预制整书夹具只证明业务协议和格式链路，不替代真实 Agent 协作。Windows 独立后置，当前实现差距及退出条件集中由[20](20-实施路线与里程碑.md)维护。

小说和剧本采用明确的内部源格式、转换报告与交付 profile；文件标准、行业惯例、制片方模板分别标注。格式范围与规范依据见[25](25-小说与剧本标准格式.md)，不将自定义 JSON 或中文短剧模板称为通行行业标准。

试点记录候选采纳率、确定规则误报、诊断覆盖、数据恢复成功与任务耗时；不得用测试集通过率宣传为所有小说的语义准确率。发布必须同时满足许可证、固定工具链、宿主兼容与签名要求。

## 8. 架构选型背景与设计目标

河图洛书需要长期管理本地目录、正文和媒体、设定集修订、Git 冲突、复杂审核及可交付版本。选择原生工作台与独立 native MCP，是为了让这些任务共用可验证的业务、文件事务和恢复底座；Codex 插件承担方法与连接，MCP Apps 承担聚焦的人类检查。

原生路线统一文件身份、事务恢复、系统凭据与长文交互；Codex 插件和 MCP Apps 通过受限接口复用这些能力。技术理由与代价见[02](02-架构选型与设计原则.md)。

设计目标是正典与生成解耦、内容独立于模型上下文、核心离线、受管入口校验、作者最终决定、版本可追溯及标准格式交付。生成供应商可选，核心仍承担自身依赖、数据完整性与安全责任；设定集锁不替代 OS 或团队权限。

## 9. 技术架构摘要

共享 Rust 内核负责领域、规则、存储、libgit2 与交付；稳定 C ABI 供 SwiftUI/AppKit、WinUI 3 和统一 Swift CLI 调用。本地 Rust MCP Server 为外部 Agent 提供标准工具与资源，协议采用范围按官方版本和宿主证据冻结。源码采用一个 Monorepo，作者内容工作区独立存放。

IP 正典和文本使用可读 JSON／Markdown／Fountain，索引可用可重建数据库；业务事实不依赖某个模型对话。插件、MCP、AXI 和 UI 资源各有版本和职责，联合设计见[27](27-Agent与Codex插件集成设计.md)，完整架构见[03](03-总体技术架构.md)。
