# 人工审核与审计

桌面审核为 V1.0 必需，MCP Apps 为可选呈现入口。作者始终保有最终决定权。

## 1. 草稿生命周期

`submitted → in_review → approved|changes_requested|rejected`；被新草稿接替的旧草稿标为 `superseded` 并保留原内容与历史决定。要求修改后生成新 draft ID，以 `parent_draft_id` 关联，不能覆盖旧草稿正文。

人工书写也可提交为待审草稿；作者自审允许，但须记录相同的版本和证据。草稿保存成功、自动检查完成与作者定稿是三个独立状态。

## 2. 审核上下文

审核屏冻结：草稿内容摘要、目标文档及基线修订、设定集修订、骨架修订、源文引用、规则集版本、报告 ID 与覆盖。展示相对当前定稿的差异、调用来源和批注。

批注包括 ID、作者、时间、引用修订、范围、正文及是否已解决。当前文本无法映射旧批注时显示在旧修订上，不静默移动批注到相似文字。

## 3. 通过与阻断

| 情况 | 定稿策略 |
| --- | --- |
| 内容摘要不符、Schema／引用损坏、越权、源文件缺失 | 硬阻断，先修复完整性 |
| 输入已变化、诊断失败或取消 | 重新校验／审阅，不沿用旧确认 |
| 规则报告部分覆盖 | 作者明确审阅覆盖缺口并记录理由；不能标为完整校验 |
| 确定性业务冲突 | 修复，或对允许例外的具体规则记录作者例外 |
| 启发式警告、Agent 语义建议 | 作者可确认已读、驳回或接受，不强迫修成算法偏好 |
| 无冲突且证据有效 | 作者一次明确通过，生成定稿修订 |

定稿在锁内重验上下文，写入不可变文本修订、`approved_revision_id`、审核决定和审计。若作者在通过前编辑了草稿，则形成新草稿并重算，而不是批准屏幕上已经过期的旧内容。

批准既不自动改设定集，也不自动 Git 提交、推送或导出。批准后继续编辑产生新当前修订，已批准旧修订仍保留；新的输入需要新的审核。

## 4. 驳回与返工

驳回保留理由、批注及可查询资源。Agent 通过资源查询或宿主支持的通知得知结果；河图不会自行运行模型、自动生成新稿或保证宿主继续对话。

要求修改应明确受影响段落与问题，不把私密备注或凭据写给外部 Agent。作者可选择可外发的批注投影，内部批注在普通工具读取中隐藏。

## 5. 审计记录

事件包括 `event_id, operation_id, workspace_id, actor_ref, action, target_refs, before_digest, after_digest, occurred_at, result, safe_parameters`。记录 Agent 的会话 ID、自报名称、工具与允许参数投影；人类决定记录本地审核人配置及可信入口。

正文和文件引用已在对象中保留，审计不重复存整段内容；秘密输入只记录“字段已提供”或安全摘要，不能把 Token 做可离线猜测的散列公开。日志失败时不能宣布审核已完整完成。

审计文件可追加并校验事件链接摘要以发现缺失或意外改写，但本地同级写权限仍可能篡改整个历史，V1 不宣称不可抵赖或监管级防篡改。

## 6. 协作冲突

两位审核者并发批准时使用草稿状态与目标基线 CAS，只接受第一个有效决定；第二个返回当前结果及冲突，不能生成两份互相覆盖的定稿。Git 合并来的审核记录不代表本机批准权限，迁移后仍检查对应证据。

定稿被撤回时不抹除历史批准，新增撤回决定并取消当前定稿指针；已导出包不可远程撤销，系统标记受影响 bundle 并提示重新交付。
