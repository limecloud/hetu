## 2. 预演如何减少昂贵试错

LibTV 的公开方法将白模视频用于运动、走位、摄影和时序，环境图用于外观，人物图用于身份与造型。这比把所有信息重复写进长 Prompt 更容易表达各素材的职责。其后续核对包括场景、摄影、身份、叙事信息、动作、口型和声音。

director-desk 进一步区分共享资源与各戏段实例，并要求接续读取真实末帧状态；计划末态、离线工程中的文字和实际输出不可混淆。只看到一个采样时点不能证明整个运动过程没有穿模或遮挡。

河图采用分级材料：剧本判断因果和对白；动态分镜判断时序和信息揭示；复杂动作或运镜按需白模；少量代表性生成判断表演与质感。不是所有镜头都需要白模，也不能把白模通过当作最终视频通过。预演自身的制作成本、错误方向和适用范围同样需要评估。

## 3. 模型适配与实际生成

Seedance 2.5 官方文档分别描述模型、模式与输入限制；2.5 与 flash 不应共享一个不区分型号的上限表。首尾帧、编辑、延长等模式的时长和画幅策略按具体能力处理，不从通用文字生成模式推断。

提示词可按镜头序号或时间顺序描述，但内容量必须匹配时长。宫格图片可作为语义参考，不能承诺逐格严格还原。复杂接触动作、人物对应、代理颜色继承、字幕／背景音乐残留等都需要看实际结果，格式检查无法替代表演验收。

河图将戏剧表达与模型调用单元分开，采用固定素材与模式计划、原任务查询、真实媒体回传和局部返工。具体价格、分辨率、素材上限及账号可用性在执行前发现；不复制第三方旧教程的固定15秒等规则，也不宣称一次生成必然可交付。

## 4. 作者如何发现细节并介入

Frame.io 官方说明支持单帧、时间区间及画面位置意见，点击意见可回到相关位置；画面批注可以在普通播放时隐藏。这适合将连贯观看和针对性核对分开，而不是在观看过程中持续塞入提示。

Kitsu 的相关源码体现资产到镜头、镜头到资产的查询以及媒体版本比较。河图据此组织按人物出场、前后场次、版本变化及具体疑点的核对视图，不引入排期、云端团队或人工维护的画布。

Figma 的对象选择只解决局部指向问题，不能承担短剧的时间、声音、表演和因果审阅。作者应能看到完整原文与音画，自主检查 AI 未标记的内容；Agent 摘要不能变成唯一可见结果。

## 5. 对话与界面的衔接

MCP Apps 提供 `ui/update-model-context` 与 `ui/message` 等机制。上下文更新供未来轮次使用，不等于启动生成；发送消息由宿主控制，其受理也不证明后续业务已经完成。具体用法及字段以固定版本 SDK 与当前宿主协商结果为准。

河图延伸已有公开 TaskFeedback 和同任务返工合同，绑定固定文字、图片区域、媒体区间或多个相关对象。作者只写自然语言，软件保存精确引用；Agent 解释并组织修改，作者比较返工结果。原生复制、Apps 局部交互与普通工具读取是同一条链路的不同入口。
