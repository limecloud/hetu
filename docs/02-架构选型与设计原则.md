# 架构选型与设计原则

河图洛书采用原生客户端、共享本地内核和开放 Agent 接口，围绕作者对内容的持有权、正典约束、离线创作及可追溯交付设计。

## 1. 设计目标

1. 作者掌握设定集和定稿；外部 Agent 只能在授权范围内读取与提交候选内容。
2. 核心写作、规则校验、审核、本地版本和导出不依赖网络、模型或第三方账号。
3. GUI、CLI、MCP 共用应用用例、事务和权限，平台只保留原生交互差异。
4. 文件透明可读、引用稳定、修订可追溯，作者内容与软件源码分离。
5. 简体中文为默认体验，英文具有同等功能覆盖；语言不影响内容身份和版本。
6. 软件引导安装与交接，作者在所选外部客户端对话；专用 Skills 约束回传方式，候选采纳和定稿由作者分别决定。

## 2. 技术选择与代价

| 选择 | 设计理由 | 工程代价与约束 |
| --- | --- | --- |
| Rust Core 与稳定 C ABI | 共享规则、文件事务、libgit2 和交付实现 | 所有权与类型约束；unsafe/FFI 审计、事务恢复与跨平台测试 |
| SwiftUI/AppKit 与 WinUI 3 | 原生长文编辑、系统文件交互、键盘与辅助功能 | 两套 UI 独立开发，业务语义共用 |
| 统一 Swift CLI | 复用参数编排与 Swift 桥接，提供独立人工及自动化入口 | Windows runtime、控制台与干净系统分发必须验收 |
| 独立 stdio MCP Server | 宿主按需启动；业务记录独立于窗口和连接生命周期 | 协议库维护、版本协商和宿主兼容需单独验收 |
| 外部 Agent＋专用 Skills | 复用作者已有客户端和生成能力，河图洛书只组装任务 Prompt 与展示验收 | 安装和能力逐宿主适配，复制、回传与恢复需清晰引导 |
| MCP Apps＋按需 Node.js 局部页面 | 对话内聚焦选择与必要的大画布比较共用业务记录 | 两种桥接分别适配；回环页面需配对和会话隔离，不增加必装后台服务 |
| 文件为权威，SQLite 为可重建索引 | 支持直接备份、Git 审阅与标准交付 | 多文件一致性依赖进程锁、CAS 和恢复日志 |
| 规则提取与可解释校验 | 核心不依赖生成服务，问题可回到明确证据 | 中文自由文本存在歧义，候选、未知与覆盖必须可见 |
| 独立可选多媒体插件 | 网络、费用和供应商适配与核心隔离 | 结果仍需来源、审核和权利状态管理 |

Rust 用于共享内核，利用所有权、类型与 Result 管理内存和失败；unsafe 限制在经过审计的 ABI 边界。系统调用、文件事务、FFI 和业务授权仍需独立验证。文件权威是数据持有与版本审阅的选择，不否认嵌入式数据库的适用性。

## 3. 原生工作台与插件的分工

原生工作台负责建书、长文编辑、设定集维护、任务准备、文件事务、Git 冲突与完整验收。Codex Plugin 或其他宿主的 Skills＋MCP 负责方法与连接分发，外部客户端承担所有 AI 对话与生成。MCP Apps 负责宿主内局部选择；需要较大页面时按需启动 Node.js 并通过内置浏览器访问，二者共同调用内核，不保存第二套业务事实。

作者写作是桌面默认路径，原生编辑、保存和定稿独立成立。AI 协作按需提供任务入口、上下文组织、专用 Skill、候选比较和来源追踪；外部 Agent 返回独立参考稿，作者可自行改写或明确采纳所选内容。采纳只形成写作稿，独立定稿固定作者确认的修订。具体交接与回退见[27](27-Agent与Codex插件集成设计.md)。

浏览器具备受授权文件访问、离线缓存和 Native Messaging 等能力。河图洛书采用原生路线，是为了统一所需的系统集成和恢复语义；浏览器性能、权限或生命周期的具体差异以对应平台合同为准。技术证据见[浏览器与原生能力研究](research/04-浏览器与原生能力研究.md)。

## 4. Swift CLI 边界

Swift CLI 使用跨平台 Foundation 子集，通过 C ABI 调用 Core；SwiftUI、AppKit 与 Windows App SDK 不属于 CLI 的运行前提。macOS 与 Windows 分别构建产物，分别适配终端、信号和凭据，保持命令、JSON 和退出码一致。

Swift 官方提供 Windows 工具链；语言可跨平台不等于所有第三方依赖可用。发布要求覆盖 SwiftPM 构建、C ABI 链接、中文路径、管道、Ctrl+C、TTY 确认及无开发环境启动，详见[13](13-内核ABI与CLI合同.md)。

## 5. 工程原则

- KISS：采用本地模块化单体，以完整人工闭环为最小业务切片。
- YAGNI：不预建云账号、实时协作、消息代理、移动端或插件市场。
- DRY：领域规则、Schema、错误、文案键与语义资源各有唯一来源。
- SOLID：领域判断、应用编排、存储、平台与表现职责清晰，接口围绕实际用例建立。
