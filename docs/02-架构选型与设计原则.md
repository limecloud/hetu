# 架构选型与设计原则

河图洛书采用原生客户端、共享本地内核和开放 Agent 接口，围绕作者对内容的持有权、正典约束、离线创作及可追溯交付设计。

## 1. 设计目标

1. 作者掌握设定集、正式采纳与定稿；外部 Agent 在授权范围内读取资料、维护协作稿及未采用资料、提交候选。
2. 核心写作、规则校验、审核、本地版本和导出不依赖网络、模型或第三方账号。
3. GUI、CLI、MCP 共用应用用例、事务和权限，平台只保留原生交互差异。
4. 文件透明可读、引用稳定、修订可追溯，作者内容与软件源码分离。
5. 简体中文为默认体验，英文具有同等功能覆盖；语言不影响内容身份和版本。
6. 软件引导安装与交接，作者在所选外部客户端对话；专用 Skills 约束回传方式，候选采纳和定稿由作者分别决定。
7. 创作库登记独立小说、剧本和视频；来源关系不成为强制父子层级，工作区不等于小说，跨对象关联不扩权。
8. 人持续参与品味、创意和细节判断；用适合问题的预演降低昂贵试错，用实际音画验证成片，不以模型状态代替结果。

### 1.1 核心价值的设计判据

[产品核心价值](01-产品需求PRD.md#1-产品定义)要求 AI 能围绕持续积累的作品工作。评审功能和接口时，检查以下结果：

- **可积累**：作品事实、固定来源、修订与作者决定保存在作者持有的工作区；模型或会话变化后，可从已有记录接续。
- **可理解**：候选说明所用来源与基线，作者能够查看差异、适用范围及需要重新核对的依据。
- **可选择**：收到候选、反馈、采纳和定稿分别记录；作者可自行重写、局部采用或放弃，既有正文与未保存编辑受到保护。
- **可继续创作**：反馈绑定具体成果，返工沿原任务接续；失败或未知结果按原操作恢复，历史候选与定稿保持可查。

授权、修订一致性、采纳、定稿及恢复属于共享内核的确定性责任，创作方法由 Skills 提供，理解、规划与生成由外部 Agent 执行。原生界面优先呈现阅读、比较、意见与决定，其次提供作者编辑；结构化资料由 Agent 准备，不要求作者维护内部模型或重新填写对话已有信息。

### 1.2 全软件联动的设计判据

1. **机器入口先于页面流程**：先定义应用动作、范围、输入输出、预览及恢复，再投影到 CLI/MCP、Skills 和界面。建书筹备也可从无作品、无桌面窗口的状态发起，不能要求先在 GUI 制造任务。
2. **操作与决定分开**：建书、整理卷章、导入解析、资料填写、检查和交付准备由 Agent 执行；涉及采纳、定稿或外部副作用时，Agent 准备确切提案，作者只审阅所需决定。需要批准不意味着每一步都要作者操作。
3. **全页上下文交接**：书库、详情、编辑器、资料、审核、版本、交付、设置及异常状态都提供与当前对象绑定的 AI 入口。上下文引用不是授权；交接不自动外发整部作品。
4. **不依赖视觉操控**：Skills + CLI/MCP 完成正常业务。Computer Use 只验证界面或在其他入口均不可用时兜底；机器接口缺失列为缺陷并修复，不能靠点击 UI 通过业务验收。
5. **共享一个状态**：外部 Agent、原生端、Apps 和局部页面读写同一内核事实；界面能看到机器操作的成果、待审项和失败恢复，Agent 能读回作者公开意见与决定。
6. **不增加第二个 Agent**：软件组织作品、权限和确定性事务，不在内部规划、生成或维持自动对话循环。默认使用 AI 不等于强迫作者使用 AI，手动编辑仍独立可用。

权限按读取、草稿维护、操作准备、明确授予的执行及作者决定分别建模，不用单一“Agent 一律禁止正式操作”覆盖全部业务，也不提供通用作者提权开关。跨对象、扩大范围、覆盖原文及外部副作用的规则由 Core 检查。合同见[30第25节](30-应用API详细设计.md#25-全软件联动与操作提案合同)，实现准入见[20](20-实施路线与里程碑.md)。

## 2. 技术选择与代价

| 选择 | 设计理由 | 工程代价与约束 |
| --- | --- | --- |
| Rust Core 与稳定 C ABI | 共享规则、文件事务、libgit2 和交付实现 | 所有权与类型约束；unsafe/FFI 审计、事务恢复与跨平台测试 |
| SwiftUI/AppKit 与 WinUI 3 | 原生长文编辑、系统文件交互、键盘与辅助功能 | 两套 UI 独立开发，业务语义共用 |
| 统一 Swift CLI | 复用参数编排与 Swift 桥接，提供独立人工及自动化入口 | Windows runtime、控制台与干净系统分发必须验收 |
| 独立 stdio MCP Server | 宿主按需启动；业务记录独立于窗口和连接生命周期 | 协议库维护、版本协商和宿主兼容需单独验收 |
| 外部 Agent＋专用 Skills | 复用作者已有客户端和生成能力，河图洛书提供任务、按需上下文、候选交接与反馈接续 | 安装和能力逐宿主适配，复制、回传与恢复需清晰引导 |
| MCP Apps＋按需 Node.js 局部页面 | 对话内聚焦选择与必要的大画布比较共用业务记录 | 两种桥接分别适配；回环页面需配对和会话隔离，不增加必装后台服务 |
| 文件为权威，SQLite 为可重建索引 | 支持直接备份、Git 审阅与标准交付 | 多文件一致性依赖进程锁、CAS 和恢复日志 |
| 规则提取与可解释校验 | 核心不依赖生成服务，问题可回到明确证据 | 中文自由文本存在歧义，候选、未知与覆盖必须可见 |
| 独立可选多媒体插件 | 网络、费用和供应商适配与核心隔离 | 结果仍需来源、审核和权利状态管理 |

Rust 用于共享内核，利用所有权、类型与 Result 管理内存和失败；unsafe 限制在经过审计的 ABI 边界。系统调用、文件事务、FFI 和业务授权仍需独立验证。文件权威是数据持有与版本审阅的选择，不否认嵌入式数据库的适用性。

## 3. 原生工作台与插件的分工

原生工作台首先负责成果阅读、结构与差异可视化、审核及必要确认，其次提供长文编辑和手动优化。建书、资料与结构维护、任务准备、版本及交付准备经共享应用用例向 Agent 开放。Codex Plugin 或其他宿主的 Skills＋MCP 负责方法与连接分发，外部客户端承担所有 AI 对话与生成。MCP Apps 负责宿主内局部审阅；需要较大页面时按需启动 Node.js 并通过内置浏览器访问，二者共同调用内核，不保存第二套业务事实。

默认协作路径由外部 Agent 操作、作者可视化审阅构成。作者可自行改写或明确采纳所选内容；采纳只形成写作稿，独立定稿固定作者确认的修订。原生编辑、保存和定稿仍能独立使用，不要求作者先使用 AI。具体交接与回退见[27](27-Agent与Codex插件集成设计.md)。

浏览器具备受授权文件访问、离线缓存和 Native Messaging 等能力。河图洛书采用原生路线，是为了统一所需的系统集成和恢复语义；浏览器性能、权限或生命周期的具体差异以对应平台合同为准。技术证据见[浏览器与原生能力研究](research/04-浏览器与原生能力研究.md)。

## 4. Swift CLI 边界

Swift CLI 使用跨平台 Foundation 子集，通过 C ABI 调用 Core；SwiftUI、AppKit 与 Windows App SDK 不属于 CLI 的运行前提。macOS 与 Windows 分别构建产物，分别适配终端、信号和凭据，保持命令、JSON 和退出码一致。

Swift 官方提供 Windows 工具链；语言可跨平台不等于所有第三方依赖可用。发布要求覆盖 SwiftPM 构建、C ABI 链接、中文路径、管道、Ctrl+C、TTY 确认及无开发环境启动，详见[13](13-内核ABI与CLI合同.md)。

## 5. 工程原则

- KISS：采用本地模块化单体，以完整人工闭环为最小业务切片。
- YAGNI：不预建云账号、实时协作、消息代理、移动端或插件市场。
- DRY：领域规则、Schema、错误、文案键与语义资源各有唯一来源。
- SOLID：领域判断、应用编排、存储、平台与表现职责清晰，接口围绕实际用例建立。

## 6. 创作对象、预演与审阅的取舍

小说、剧本、视频按事实拥有者拆分：正文与对白由各自文稿持有，镜头制作、预演及剪辑由视频项目持有，来源关系固定版本。导航可以独立，不要求新建三个仓库或复制三份正文。旧项目投影到创作库，保留身份与路径；显式迁移另行预演，不将界面改名做成数据搬迁。

动态分镜用于节奏、揭示及声音时机，白模用于空间、遮挡与调度，真实生成用于身份、表演、动作与质感；选择最小能回答当前问题的材料，不强制逐镜白模。作者可随时查看完整成果和未标记位置，不限于 Agent 摘要。桌面提供观看、比较和位置反馈；复杂建模、渲染及剪辑由外部 Agent 的机器工具执行。

预演认可、媒体选用、文稿定稿与成片确认分别记录。媒体生成是有费用且可出现未知结果的外部副作用，不能用本机事务宣称撤销或退款。固定计划、原调用查询和实际媒体核验先于自动重试；适配器能力不足时明确阻断。具体设计见[37](37-创作库与小说剧本视频设计.md)，研究边界见[research/13](research/13-短剧预演视频与人工审阅研究.md)。
