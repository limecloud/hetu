# 构建分发与运维

本章定义独立制品、工具链、构建、签名、安装与升级要求。精确工具链和依赖摘要随发行清单锁定。

## 1. 工具链与独立产物

| 产物 | 工具链路线 | 运行依赖 |
| --- | --- | --- |
| Rust Core／C ABI | Rust 1.93.1、Cargo、平台 native 链接工具 | 固定 native 依赖 |
| macOS App | Swift 6 系列、Xcode 与 macOS SDK | 系统框架及随包内核 |
| Windows App | C#、WinUI 3、.NET 10 LTS | 明确的 .NET／Windows App SDK 分发模式及内核 |
| 跨平台 Swift CLI | SwiftPM、共享 Swift Bridge | 必需 Swift runtime、C ABI 与 native 依赖 |
| Rust MCP Server | 与 Core 相同 native 工具链 | Core 及选定协议库，无 GUI 要求 |
| MCP Apps／宿主扩展资源 | 局部交互前端构建、专用 Skills 与宿主适配包 | 宿主能力独立验收，未安装不影响人工创作 |
| Node.js 局部页面 | 随功能制品分发的固定 runtime、页面与受限 IPC 代理 | 按需启动；原生编辑不依赖此进程，不要求用户全局安装 Node.js |

Mac 一键开发入口为 `./dev-mac.command`，也可在 Finder 双击。脚本检查本机工具链，构建任务页面、Rust 内核、MCP 和 Mac 客户端，再打开独立的 `build/native/HetuDev.app`；不启动官网或 Windows。`--check` 只检查工具链，`--build-only` 只构建。开发版已运行时保留当前会话；重新编译前正常退出开发版。

完整原生测试入口为 `python3 "tools/build-native.py" --test`。该入口构建 Swift Bridge／CLI／Mac 客户端并执行桥接、内核及原生测试，输出 `build/native/Hetu.app` 和独立 `build/native/bin/hetu-mcp`；App 内对应助手位于 `Contents/Helpers/hetu-mcp`。MCP 复用静态链接的 Rust 内核，不加载 Swift 运行时或 App 私有资源，单独二进制通过 `--workspace` 绑定作品。开发产物仅做 ad-hoc 签名，正式签名与公证不由该结果推导。

Mac 页面运行时从本机已有 Node.js `>=24.21.0 <26` 及同一安装目录的 LICENSE 装配；`--node-runtime` 可指定精确可执行文件，脚本不安装或修改全局 Node。产物位于 `Contents/Helpers/node`，许可与签名后摘要记录于 `Contents/Resources/ThirdParty/`。页面脚本及摘要位于 `Hetu_HetuTaskViewAssets.bundle/local/`。Node 只随显式任务页面启动，不是编辑器、Swift CLI 或独立 MCP 的运行前提。

软件 release 清单记录每个产物版本、源修订／树摘要、合同／ABI 版本、OS、架构、依赖和最终 SHA-256。同一发行组合必须兼容，但不强迫用户同时安装 GUI、CLI、MCP 与插件。

## 2. 构建入口设计

先由 Cargo 构建 Core、C ABI 和 MCP，再 staging 头文件、module map 与库；SwiftPM 和原生 App 消费固定产物。共享内核不得由不同入口各自下载不同 libgit2 或使用不同构建选项。

工程入口必须提供明确的本地构建、合同检查、资源生成、内核测试、Swift CLI、双端原生测试和打包入口；每个入口说明可运行平台及副作用。使用指南直接引用真实构建入口。

## 3. 支持矩阵

V1 目标 macOS 14+ arm64、Windows 11 x64；Intel macOS、Windows ARM64 和 Linux CLI 在实际依赖与原生验收后单独声明。二进制按 OS／架构分别构建，不能把“Swift 跨平台”当作单包通用或免运行时部署。

Windows Swift CLI 必须在未装 Swift 工具链、.NET 或桌面 App 的环境启动，验证 runtime DLL、native 库路径、Unicode、Ctrl+C 和 JSON 重定向。macOS CLI／MCP 不依赖 Xcode 安装或桌面应用私有资源路径。

## 4. 安装渠道

优先提供签名的原生独立下载包；macOS App 公证，Windows 验证发布者和依赖。安装／卸载只处理软件与用户选择的偏好，不删除作者工作区。

可选 npm 启动器作为便捷渠道：按 OS／CPU 选择精确版本原生产物，以参数数组转发并保留终端、输出、退出码和取消；启动器不承载业务，不执行 postinstall 网络下载或在用户机器编译。npm 不是使用核心功能的必装条件。

Codex 插件是宿主侧的 skills／MCP／Apps 声明与资源，不能代替 native CLI 的安装和 ABI 兼容检查，也不在插件安装时静默获得文件与 Git 权限。

## 5. 升级与数据兼容

应用升级与内容格式升级分开。新程序先读取 Schema 版本，只在支持范围内写入；未知主版本只读。内容升级由作者确认、备份、预演后执行，失败保留原项目。

回退旧程序不能自动降级内容。CLI、GUI 或 MCP 发现正在运行的不兼容写入口时阻止同时写入，提示用户完成／关闭旧任务。运行时授权与凭据不得通过内容迁移传播到其他机器。

## 6. 发布门禁与诊断

固定源输入 → 合同／资源检查 → 测试 → 分平台构建 → 签名 → 干净系统安装 → 完整旅程 → 最终摘要与发布说明。签名后摘要才作为最终制品摘要。

CI 执行构建与测试，正式签名包由授权维护者手动构建，实际外部发布需单独授权。无证书、宿主或目标 OS 时明确 `blocked`，不能以开发包替代正式签名验收。默认不设置自动更新和正文遥测；诊断遵循[18](18-安全与隐私.md)。

### 6.1 GitHub Actions

`.github/workflows/ci.yml` 在 `main` 推送、Pull Request 和手动运行时执行原生与网页测试。原生任务使用 macOS arm64、Xcode 26.3 和锁定 Rust；网页任务在 Linux 检查网站及任务页面。普通 CI 不读取发布凭据。

在仓库 **Actions → macOS signed package → Run workflow** 选择 `main`，运行 `.github/workflows/macos-release.yml`。该流程使用 Node.js 24.21.0、Rust 1.93.1 与 Xcode 26.3，依次执行工具测试、资源核对、release 原生测试、Developer ID 签名、App 与 DMG 公证及 Gatekeeper 检查。成功后从该次运行的 `hetu-macos-arm64` artifact 下载 DMG、ZIP、`release-manifest.json` 和 `SHA256SUMS`；手动运行仅生成 Actions 附件；推送匹配 `package.json` 版本的 `v*.*.*` 标签时，流程核验最终 SHA-256 后创建 GitHub Release 并上传相同安装包，不上架 App Store。已公开版本不可覆盖。

运行前在仓库 **Settings → Secrets and variables → Actions** 配置以下 Repository Secrets。全部必填，值仅保存在 Secrets，不进入源码或日志。

| Secret | 内容 |
| --- | --- |
| `APPLE_CERTIFICATE` | 包含证书及私钥的 Developer ID Application `.p12`，编码为单行 Base64 |
| `APPLE_CERTIFICATE_PASSWORD` | 该 `.p12` 的导出密码 |
| `APPLE_SIGNING_IDENTITY` | 证书完整名称，格式为 `Developer ID Application: <组织名称> (<TEAM_ID>)` |
| `APPLE_TEAM_ID` | 该证书所属 Apple Developer 团队标识 |
| `APPLE_ID` | 拥有该团队公证权限的 Apple 账号 |
| `APPLE_PASSWORD` | 该账号的 App 专用密码，不能使用 Apple 登录密码 |

签名使用当次任务创建的临时钥匙串，结束时恢复搜索列表并清理私钥，无需配置固定 `KEYCHAIN_PASSWORD`。内嵌 Node.js 使用独立 JIT entitlement，其余代码启用 Hardened Runtime 和安全时间戳；Node 摘要在重签后更新。版本从 `package.json` 读取并与 `Cargo.toml` 核对。

`tools/build-native.py --configuration release` 为 Rust、Swift、测试和资源装配选择相同配置；默认 `debug`。正式流程固定使用 `--swift-scratch-path "build/release-swift"`，`tools/release-macos.py` 从该目录核对 App 资源，拒绝混用其他构建缓存。

工具与配置验证命令：

```bash
python3 -m unittest discover -s "tests/tooling" -v
python3 "tools/release-macos.py" --check
```

第二条命令需要 macOS arm64 和上述 Secrets。公证提交与结果保存在当次运行的 `macos-notarization-receipt` artifact；等待超时后沿其中的原提交 ID 查询 Apple 状态，不以重新上传代替恢复。已有发行输出或公证证据目录时脚本停止，保留原结果；新任务使用干净 checkout。

## 7. 局部交互与接入包制品

Apps HTML、共享交互组件、Node.js runtime／页面代理、Skill 方法源与各宿主适配分别记录版本、依赖、许可和产物摘要。Node.js 在受支持平台随功能制品分发，签名、架构、子进程启动、停止和干净用户环境分别验收；不在首次交互时执行网络包安装或借用户全局 Node.js 掩盖依赖缺失。

随附方法包以 `python3 "tools/verify-skills.py"` 离线核对发现入口、引用可达性、来源与许可摘要、完整性目录及安装器文件预算；Mac 构建在资源装配前执行同一门禁。原生安装器另对隔离目录中的完整安装、残包、版本和官方安装回执执行验证。

Mac 打包从受管源码精确装配 Swift 资源与 App 内资源目录，逐文件核对文件集和 SHA-256，禁止把新版本合并复制到旧资源树。装配先在同父目录准备并核验新副本，再替换生成目录；失败保留或恢复上一份资源。`build/native/resource-manifest.json` 记录随包 Skills 版本及逐文件摘要，生成清单不能代替源码完整性门禁。资源装配后完成助手与 App 签名，最终签名另行核验；不以 SwiftPM 增量构建成功推断资源已更新。

Apps 可打包为自带脚本和样式的单文件资源，本地网页使用相同构建来源的组件并采用自己的会话桥接。页面服务与 native MCP 分开发布能力，不因有 HTTP 页面就开放 HTTP MCP。插件安装缓存、新会话实际发现及包更新分别验证，软件内指南只展示当前发行制品的真实安装入口。

本机 Apps 资源由 `npm run build:task-view` 生成到 `apps/mcp/resources/`，包含单文件 HTML、SDK 版本、源码摘要与产物摘要；本地宿主同时生成到 `apps/task-view/resources/local/`。Apps 随 Rust 编译内嵌，Mac 构建入口核对两套资源摘要；纯 Cargo 构建与独立 MCP 无 Node.js 运行依赖。修改资源源码后执行 `npm run check --workspace @hetu/task-view` 与 `npm run test:task-view`，分别验证产物一致性及沙箱桥接、真实 stdio 回读、配对／停止、错误恢复和双语布局。`tools/build-native.py --test` 另以装配后的 runtime 执行 Swift 父进程、HTTP 配对、真实 Core 保存及关闭撤权测试。实际宿主兼容仍按指定客户端及版本独立验收。
