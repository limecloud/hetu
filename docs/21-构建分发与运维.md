# 构建分发与运维

## 随包基础能力装配

基础能力清单固定在 `contracts/baseline.json`，由Core和桌面构建共同消费。构建核对各作品类型要求的核心动作、随包工作面与源码模块；缺失时报错，不引导作者安装可选插件补齐。基础模块随应用统一版本交付，不自动写入用户创作插件目录。独立CLI/MCP读取同一清单；诊断状态仅表示合同完整性，运行与业务验收独立执行。架构见[39](39-Electron与插件优先重构架构.md#无额外插件的基础产品)。


v0.9.0的GitHub Actions按macOS arm64、Windows x64和Linux x64分别构建原生Rust助手及Electron包。Windows安全文件访问使用句柄相对目录适配，Linux复用Unix实现；每个平台分别核验构建、独立CLI、包体与启动。macOS继续使用Developer ID及Apple公证；Windows和Linux附件按实际签名状态标记，平台交互与干净系统验收独立记录。

本章定义独立制品、工具链、构建、签名、安装与升级要求。新工作台采用[39](39-Electron与插件优先重构架构.md)的Electron＋Rust及插件贡献模型。精确工具链与依赖摘要随各自制品清单锁定。

## 1. 工具链与独立产物

| 产物 | 工具链路线 | 运行依赖 |
| --- | --- | --- |
| Rust Core | Rust 1.93.1、Cargo、平台 native 链接工具 | 固定 native 依赖 |
| Electron桌面目标 | 固定Electron、TypeScript、前端依赖与平台打包工具 | 随包Chromium/Node、Rust App Server及native依赖 |
| Windows桌面目标 | 共同Electron前端与匹配架构的Rust工具链 | 平台打包、签名及实机验证，不新增WinUI产品 |
| 独立Rust CLI目标 | Cargo、Core与CollaborationHub | native依赖，无Electron／Swift／.NET前提 |
| Rust MCP Server | 与 Core 相同 native 工具链 | Core 及选定协议库，无 GUI 要求 |
| MCP Apps／宿主扩展资源 | 局部交互前端构建、专用 Skills 与宿主适配包 | 宿主能力独立验收，未安装不影响人工创作 |
| Node.js 局部页面 | 随功能制品分发的固定 runtime、页面与受限 IPC 代理 | 按需启动；桌面编辑不依赖此进程，不要求用户全局安装 Node.js |

macOS 一键开发入口为 `./dev-mac.command`，也可在 Finder 双击，仅构建和启动 Electron 开发版。脚本检查 Rust、Xcode Command Line Tools、Python 3、Node.js `>=25 <26` 与同一安装的 LICENSE，按需安装锁定依赖，构建共享任务页面，再复用 `npm run package:desktop` 装配 App Server、独立 CLI／MCP、插件宿主及工作台。应用与清单位于 `output/electron-packages/` 的独立目录，实际 `.app` 路径由终端输出。`--check` 只检查工具链，`--build-only` 只构建，`--node-runtime` 指定已有 Node；脚本不安装或更新系统工具链。构建锁使用 `build/electron/dev-mac.lock`；Electron 开发版已运行时仅激活当前会话，重新编译前正常退出。

Cargo产物可通过 `CARGO_TARGET_DIR` 指定隔离目录；默认使用仓库 `target`。Core、MCP、装配及测试使用同一目录，不从另一个缓存复制旧内核。构建和验收期间保留所选Rust目录及日志，不能同时清理仍在使用的缓存。

软件 release 清单记录每个产物版本、源修订／树摘要、合同／ABI 版本、OS、架构、依赖和最终 SHA-256。同一发行组合必须兼容，但不强迫用户同时安装 GUI、CLI、MCP 与插件。

macOS 图标通过 `uv run tools/export-macos-icon.py` 从 `assets/brand/app-icon-1024.png` 导出，统一更新 `assets/brand/icons/macos/` 的透明边距、尺寸与ICNS，并同步 `assets/manifest.json` 摘要。桌面装配使用其中的 `Hetu.icns`。

Electron制品清单包含独立Rust CLI、MCP、App Server、插件CLI、共享合同及所选方法资源，实际安装位置由制品清单公布；当前装配差距和退出证据由[20第6节](20-实施路线与里程碑.md#6-持续协作的实施准入)维护。独立 CLI／MCP 包也分别核验依赖和许可，不依赖 GUI 进程启动。

## 2. 构建入口设计

独立Rust CLI源码为 `apps/cli/src/main.rs`。以下入口不构建或启动桌面，输出仓库 `target/debug/hetu` 和 `target/debug/hetu-mcp`；自定义Cargo目标目录时按实际输出定位：

```bash
cargo build --locked --jobs 2 --package hetu-cli --package hetu-mcp
"target/debug/hetu" --client codex collaboration inspect
cargo test --locked --jobs 2 --package hetu-cli --package hetu-mcp -- --test-threads=2
```

CLI与MCP分别直接复用Core。独立CLI不加载动态Core或Swift。开发二进制通过不等于已安装工具更新、目标平台干净系统验收或签名分发通过；本机设置的宿主Owner接入边界见[13第4节](13-内核ABI与CLI合同.md#4-独立cli)。

新桌面先由Cargo构建App Server、独立CLI/MCP，再构建Electron主进程、preload、工作面与插件资源；最终清单固定同一组Core、合同、前端和方法资源。共享内核不得由不同入口各自下载不同 libgit2 或使用不同构建选项。

Electron 开发装配合同见[插件20第10节](plugin/20-首期可执行合同与开发入口.md#10-electron-开发制品装配合同)。独立 Node 25+ 与 Electron 的内置 Node 分别装配；插件后端不能使用已验证不满足网络权限要求的旧运行时。独立开发应用采用不同 Bundle ID 及配置身份，普通资源目录向 Node CLI 提供真实脚本文件；ASAR 不作为权限边界。

本机设置服务使用独立 `LocalSettings` 私密目录；开发时 `HETU_LOCAL_SETTINGS_DIR` 可指定绝对目录，`HETU_DESKTOP_PROFILE` 在未另指定时将其放入隔离配置。机器交接携带同一目录，不能和旧原生 UserDefaults／方案混用。`integrations/catalog.json` 和完整 `integrations/codex/` 同版装配，纳入源码及制品摘要；只安装作者所选包。`HETU_INTEGRATIONS_DIR`、`HETU_CODEX_BINARY` 仅用于可信开发／隔离测试的资源与可执行文件定位，不是业务参数。

以下命令在当前目标系统装配独立开发应用；`--node` 指向同 OS／架构的 Node 25+，其安装目录须保留 LICENSE。省略 `--node` 时使用运行脚本的 Node。输出位于 `output/electron-packages/` 的唯一新目录，清单记录实际路径和摘要；不会安装覆盖或发布。

```bash
npm run package:desktop
```

本机覆盖安装使用 `npm run package:desktop -- --local-install`，沿用正式应用名称 `Hetu.app` 与 Bundle ID `run.limeai.hetu`，使用ad-hoc签名。该模式校验并复用已安装的同版Electron运行时，清单记录运行时归档摘要；与 `--distribution` 互斥，清单种类为 `electron-local-install-package`，不满足npm官方运行时的签名和公证要求。覆盖前退出应用、备份旧包，再核对新包摘要和签名；不清除作者作品、私密设置或授权目录。

源码界面与真实开发包分别验收。下面的全套桌面测试在未提供制品时跳过打包专项；指定实际 `HETU_PACKAGED_APP` 与 `HETU_PACKAGE_MANIFEST` 后，再验证签名、分发文件摘要、随包 Rust／Node／CLI／MCP、插件和重开保持。开发签名不等同于正式签名、公证或干净系统安装验收。

```bash
npm run test:plugins
npm run test:e2e --workspace @hetu/desktop
```

工程入口必须提供明确的本地构建、合同检查、资源生成、内核测试、独立CLI、双端Electron测试和打包入口；每个入口说明可运行平台及副作用。使用指南直接引用真实构建入口。

## 3. 支持矩阵

发行构建目标为 macOS 14+ arm64、Windows 11 x64、Linux x64（Ubuntu 22.04 构建基线）。Intel macOS、Windows ARM64、其他 Linux 发行版在实际依赖与实机验收后单独声明。二进制按 OS／架构分别构建，不能把共享源码当作单包通用或免运行时部署。

目标Rust CLI必须在无Node、Swift、.NET、开发工具或桌面进程的Windows环境启动，验证native库、Unicode、Ctrl+C与JSON重定向。macOS CLI／MCP 不依赖 Xcode 安装或桌面窗口运行；启动器负责定位完整运行时及其资源。

## 4. 安装渠道

Electron开发版、正式版和独立机器包分别标识制品，开发版和正式版使用原Mac对应身份及独立配置。插件资源记录固定文件集、摘要、依赖和许可；发布前核对Electron安全更新、沙箱设置、第三方许可证和各系统签名。开发脚手架不能冒充完整安装包，新的实际命令在实现后登记，不复用原生构建命令作虚假入口。

优先提供签名的原生独立下载包；macOS App 公证，Windows 验证发布者和依赖。安装／卸载只处理软件与用户选择的偏好，不删除作者工作区。

`@limecloud/hetu` 提供 `hetu` 和 `hetu-mcp` 命令，支持 macOS 14+ arm64、Node.js 22.12+。首次运行复用精确版本的官方 App，或下载对应版本的签名 ZIP，验证 SHA-256、Developer ID 与 Gatekeeper 后缓存。启动器以参数数组转发并保留终端、输出、退出码和取消，不承载业务、不执行 postinstall 网络下载、不在本机编译。安装与环境变量见[启动器说明](../packages/npm-cli/README.md)；npm 不是使用核心功能的必装条件。

Codex 插件是宿主侧的 skills／MCP／Apps 声明与资源，不能代替 Rust CLI的安装和平台兼容检查，也不在插件安装时静默获得文件与 Git 权限。

## 5. 升级与数据兼容

应用升级与内容格式升级分开。新程序先读取 Schema 版本，只在支持范围内写入；未知主版本只读。内容升级由作者确认、备份、预演后执行，失败保留原项目。

回退旧程序不能自动降级内容。CLI、GUI 或 MCP 发现正在运行的不兼容写入口时阻止同时写入，提示用户完成／关闭旧任务。运行时授权与凭据不得通过内容迁移传播到其他机器。

## 6. 发布门禁与诊断

固定源输入 → 合同／资源检查 → 测试 → 分平台构建 → 签名 → 干净系统安装 → 完整旅程 → 最终摘要与发布说明。签名后摘要才作为最终制品摘要。

CI 执行构建与测试，正式签名包由授权维护者手动构建，实际外部发布需单独授权。无证书、宿主或目标 OS 时明确 `blocked`，不能以开发包替代正式签名验收。默认不设置自动更新和正文遥测；诊断遵循[18](18-安全与隐私.md)。

### 6.1 GitHub Actions

`.github/workflows/ci.yml` 在 `main` 推送、Pull Request 和手动运行时执行 Electron、Rust及网页测试。Electron 使用 macOS arm64、Node.js 25.0.0 和 Rust 1.93.1，核对版本、共享页面、插件与真实桌面交互；普通 CI 不读取发布凭据。Rust、插件与Electron界面分别核验。

`.github/workflows/electron-release.yml` 分别在 macOS arm64、Windows x64、Linux x64 runner 构建 Electron 包。手动运行仅生成 Actions 附件；推送匹配所有 workspace 版本的 `v*.*.*` 标签时，全部平台通过对应测试、打包与随包专项后统一创建 GitHub Release。Mac 另须签名与公证。源码固定当次 Git SHA，公开版本不可覆盖。

同一工作流的`npm`任务依赖GitHub Release发布成功，使用Node.js 25.0.0，在校验固定标签、源码、公开Release及Mac签名公证清单后发布`@limecloud/hetu`。npm包不安装工作区依赖，发布前执行启动器与发行守卫测试；固定包摘要与registry回读一致且`latest`指向本版才通过。已有相同字节的版本按原包恢复，不覆盖不同字节。npm失败时在原Actions运行中选择“Re-run failed jobs”，不改写标签或重新发布GitHub附件。

npmjs包设置中的可信发布者使用GitHub组织`limecloud`、仓库`hetu`和工作流文件`electron-release.yml`，允许`npm publish`；对应任务仅授予`contents: read`与`id-token: write`，通过OIDC取得短期发布身份并生成provenance。也可在仓库Actions Secrets配置仅授权该包发布的`NPM_TOKEN`，作为`NODE_AUTH_TOKEN`传入。凭据不写入工作流、包或日志，普通CI不读取npm发布凭据。

Windows 与 Linux 入口为 `node "tools/release-portable.mjs"`，使用优化 Rust 构建及正式应用名称 `Hetu`，随包核验 CLI、MCP、独立 Node 权限模型，并生成 Windows ZIP 或 Linux tar.gz。清单分别为 `release-manifest-windows-x64.json`、`release-manifest-linux-x64.json`，对应 `SHA256SUMS-windows-x64`、`SHA256SUMS-linux-x64`。两者标记 `signing: unsigned`，不冒称 Apple 公证或 Windows 发布者认证。Linux runner 通过虚拟显示运行测试；仅测试进程使用 `--no-sandbox`，产品不关闭 Chromium 沙箱。

Windows 受管目录通过 cap-std/cap-fs-ext 的目录句柄相对访问，拒绝 reparse point、设备名、ADS、尾随点与空格别名。文件身份、链接数、修改与变更时间来自 Win32 句柄；文件锁使用系统锁。Windows 没有 Unix 目录 fsync 的同等接口，文件与日志单独刷新，目录项的断电持久性不作相同保证，恢复必须回读事务和实际文件。Linux 保留 Unix openat、nofollow 与 fsync。

发布任务通过 `tools/verify-electron-downloads.py` 核验三平台齐备、同一 SHA/版本、签名状态与所有附件摘要；任一平台失败均不能发布部分版本。runner 测试与真实用户的干净系统、Windows 11、Linux 发行版和桌面环境验收分别记录。

发布入口为 `python3 "tools/release-electron.py"`，`--check` 仅检查平台、版本与凭据。入口复用 Electron 装配脚本，以 `--distribution --release` 构建优化的 Rust 助手和正式身份 `run.limeai.hetu`／`Hetu.app`，与开发身份 `run.limeai.hetu.dev` 的配置隔离。App 内的独立 CLI、MCP、App Server、插件 CLI 和 Node 位于 `Contents/Resources/bin/`，无需桌面进程运行。

运行前在仓库 **Settings → Secrets and variables → Actions** 配置以下 Repository Secrets。全部必填，值仅保存在 Secrets，不进入源码或日志。

| Secret | 内容 |
| --- | --- |
| `APPLE_CERTIFICATE` | 包含证书及私钥的 Developer ID Application `.p12`，编码为单行 Base64 |
| `APPLE_CERTIFICATE_PASSWORD` | 该 `.p12` 的导出密码 |
| `APPLE_SIGNING_IDENTITY` | 证书完整名称，格式为 `Developer ID Application: <组织名称> (<TEAM_ID>)` |
| `APPLE_TEAM_ID` | 该证书所属 Apple Developer 团队标识 |
| `APPLE_ID` | 拥有该团队公证权限的 Apple 账号 |
| `APPLE_PASSWORD` | 该账号的 App 专用密码，不能使用 Apple 登录密码 |

签名使用临时钥匙串，结束时恢复搜索列表并清理私钥。Electron 与独立 Node 的 JIT 权限单独声明，全部代码启用 Hardened Runtime 和安全时间戳。App 与 DMG 分别公证、装订并通过 Gatekeeper；随后重算最终文件摘要，下载包为 `Hetu-<版本>-macos-arm64.dmg`、同名 ZIP、`release-manifest.json` 和 `SHA256SUMS`。清单固定 Electron 类型、源码、随包资源、签名和最终下载摘要，npm 启动器只接受对应的正式身份与签名。

工具与配置验证命令：

```bash
python3 -m unittest discover -s "tests/tooling" -v
node "tools/verify-release.mjs"
python3 "tools/release-electron.py" --check
```

最后一条需要 macOS arm64 和上述 Secrets。公证提交及结果保存在当次运行的 `electron-notarization-receipt` artifact；结果未知沿原提交 ID 查询，不重新上传。已有发行输出或公证证据时停止，保留原结果；新任务使用干净 checkout。实际正式签名、公证、安装和 GitHub 发布结果由19、20与38分别记录，不从脚本存在推定通过。

## 7. 局部交互与接入包制品

Apps HTML、共享交互组件、Node.js runtime／页面代理、Skill 方法源与各宿主适配分别记录版本、依赖、许可和产物摘要。Node.js 在受支持平台随功能制品分发，签名、架构、子进程启动、停止和干净用户环境分别验收；不在首次交互时执行网络包安装或借用户全局 Node.js 掩盖依赖缺失。

随附方法包以 `python3 "tools/verify-skills.py"` 离线核对发现入口、引用可达性、来源与许可摘要、完整性目录及安装器文件预算；Mac 构建在资源装配前执行同一门禁。套件安装器另对隔离目录中的完整安装、残包、版本和官方安装回执执行验证。

Electron打包从受管源码精确装配App内资源目录，逐文件核对文件集和 SHA-256，禁止把新版本合并复制到旧资源树。装配先在同父目录准备并核验新副本，再替换生成目录；失败保留或恢复上一份资源。本次开发包或发行包清单记录随包 Skills 版本及逐文件摘要，生成清单不能代替源码完整性门禁。资源装配后完成助手与 App 签名，最终签名另行核验；不以增量构建成功推断资源已更新。

Apps 可打包为自带脚本和样式的单文件资源，本地网页使用相同构建来源的组件并采用自己的会话桥接。页面服务与 native MCP 分开发布能力，不因有 HTTP 页面就开放 HTTP MCP。插件安装缓存、新会话实际发现及包更新分别验证，软件内指南只展示当前发行制品的真实安装入口。

稳定接入验收固定软件、助手、CLI、方法包、插件、合同和宿主版本及摘要。先检查安装与启用，再在新会话发现真实工具，最后读取获权任务并提交隔离测试成果；前一项不能代替后一项。升级保持同一接入入口，重新核验实际制品与新会话加载；不把开发目录的新文件或旧会话中的 Skill 当成已发行版本。请求、工作副本、候选与公开反馈随内容兼容读取，私有授权不得随包复制到另一机器。

本机 Apps 资源由 `npm run build:task-view` 生成到 `apps/mcp/resources/`，包含单文件 HTML、SDK 版本、源码摘要与产物摘要；本地宿主同时生成到 `apps/task-view/resources/local/`。Apps随Rust编译内嵌，共享页面检查核对两套资源摘要；纯 Cargo 构建与独立 MCP 无 Node.js 运行依赖。修改资源源码后执行 `npm run check --workspace @hetu/task-view` 与 `npm run test:task-view`，分别验证产物一致性及沙箱桥接、真实 stdio 回读、配对／停止、错误恢复和双语布局。本地页面的HTTP配对、真实Core保存及关闭撤权由共享页面专项核验。实际宿主兼容仍按指定客户端及版本独立验收。

共享文案由 `assets/localization/shared.json` 维护，运行 `python3 "tools/verify-localization.py"` 核验双语、占位符和套件名称。
