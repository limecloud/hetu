# 小说规划插件立项分析

## 1. 结论与名称

建议以“小说规划”作为首个独立创作插件：围绕整书、卷和章，组织目标、冲突、转折、前后状态及待确认问题，让Agent整理，让作者阅读、比较和返工。它可利用现有专业数据、隔离视图和机器入口交付首版。

| 项目 | 建议 |
| --- | --- |
| 仓库名 | `hetu-novel-planner` |
| 中文名 | 小说规划 |
| 英文名 | Novel Planner |
| 插件ID | `org.wordflowlab.novel-planner` |
| 首版目标 | `0.1.0`，独立JS/TS预构建包，视图使用React，宿主采用Cordis |

名称标明服务对象和用途，便于搜索及后续同类工具区分。“AI小说生成器”容易让作者期待内置生成循环，不符合河图由外部Agent承担理解与生成的分工。独立仓库已建立，详细合同在其`docs/`维护；本篇不承担实时功能或发布状态。

## 2. 截图提供了什么参考

作者提供的截图展示卷列表、卷信息、本卷规划、详细剧情及生成状态。可借鉴的是从概览进入细节、在同一工作面查看因果结构，以及把人物、地点和势力放回具体卷的语境。

截图只能证明可见布局，不能证明其数据格式、运行机制或代码许可。本分析不推断该产品采用何种后端，也不复制截图中的作品内容。

第一版围绕“规划”形成明确边界。章节正文编辑、设定正典、关系图和时间线分别消费对应宿主或插件能力，不把截图中的全部侧栏合并为一个包。

## 3. 与当前实现的适配

核对依据为`packages/plugin-sdk/src/index.ts`、`plugins/timeline/`、`core/src/application/extensions.rs`、`contracts/actions.json`、`contracts/capability-map.json`及插件20。以下是源码合同分析，不是新插件的运行验收。

| 需求 | 当前条件与实现路径 |
| --- | --- |
| 卷／章列表、剧情分区、卡片和局部编辑 | 可用React在隔离视图中实现，不依赖Rust UI或新增原生窗口 |
| 保存规划、历史及冲突恢复 | 声明专业数据类型，经现有objects动作保存、回读及导出；使用CAS和原操作键 |
| Agent整理规划 | 稳定`hetu.plugin_access.capabilities/invoke`发现本包获权数据，不需要新建Codex插件 |
| 读取正文、设定和正式大纲 | 外部Agent以独立作品管理授权读取；插件对象读写权限不包含这些领域读取 |
| 保存正式总纲／卷纲／章纲 | 宿主已有`hetu.outlines.get/save`；save由固定管理方案承接。规划转为正式大纲须单独审阅，不从插件视图直接代行作者写入 |
| 创建正式章节和调整目录 | 交由宿主现有领域用例核验，不能用规划节点保存冒充真实章节创建 |
| 插件内直接打开宿主章节、实时读取领域目录 | 当前SDK没有这类类型化桥接；需要时补宿主合同及权限测试，不把通用request扩成任意Core代理 |
| 截图中的模型重连与生成循环 | 河图继续使用外部Agent；插件展示已保存成果和真实交接状态，不内置第二套Agent或伪造进度 |

结论是：独立规划首版可做；完整复刻截图中的一体化生成和领域操作，不能仅靠现有插件权限完成。

## 4. 首版用户旅程

1. 作者打开某部小说的规划插件，请Agent“先整理全书三卷的目标、主要冲突与首尾变化，保留已定结局”。
2. Agent发现当前包和获权能力；按另行获得的作品管理范围读取实际来源，再准备规划。
3. Agent把规划写入本插件、本作品的专业对象，回读版本及内容。保存规划不会创建正文或推进正式大纲。
4. 作者从卷列表阅读整体结构，再展开关键转折和章级计划；可直接改文字，也可沿选定成果提出意见。
5. Agent固定原规划修订，调整明确范围；遇到冲突比较新旧，结果未知时先查原操作。
6. 作者希望应用为正式大纲时，再准备现有宿主管理方案、展示具体变化并取得决定，完成后回读真实领域结果。

河图的插件成果工作面已有固定成果交接。首版优先消费这一入口；插件内部专用AI按钮若需要新的宿主能力，应先补类型化合同，不能只画一个无法完整交接的按钮。

## 5. 数据责任与建议结构

| 数据 | 所有者 | 内容 |
| --- | --- | --- |
| 小说身份、正式卷章目录、正文、正式大纲和设定 | 宿主Core | 沿用现有领域事实与作者决定 |
| 规划方案、备选安排、细分节拍和待确认问题 | 小说规划插件 | 可独立修订、审阅和导出的专业成果 |
| 临时筛选、展开、选中及未保存编辑 | 视图／受限buffer | 不当作已保存的作品修订 |

首版设计采用单个`novel_plan`聚合，内部以稳定节点组织整书、卷和章，保证调整与重排可在单对象事务内提交。节点级读取和修改由插件确定性动作提供；全方案字节与节点预算由插件合同限制。大规模分片须先解决跨对象一致性，再以数据迁移引入，不沿用早期三对象拆分建议。具体字段、预算和边界以插件仓库为准；章节数、字数预算不表示实际写作进度。

规划节点先使用本包身份；正式卷章链接由获权Agent核对后关联，不按标题或章号猜测。同一事实不维护两份长期可编辑副本：正式大纲归宿主，插件保存规划及备选；应用后记录对应关系与回执，后续变化重新核对。

当前`source_refs`可固定同作品的work、document、blueprint、asset和cue，未定义outline或volume来源。需要把某份正式大纲作为可由Core核验的固定来源时，应先补来源合同；不可把自造的引用字段当成已验证来源。完整对象及来源预算按当前安装版核验。

对象保存保证单对象事务，不能假设跨多个规划对象原子提交。不同备选方案独立保存，跨方案操作不承诺原子提交；新增、重排和归档须覆盖原键恢复。规划审阅状态不等于正文采纳或作者定稿。

## 6. 首版范围与技术选择

首版交付一套层级列表和阅读详情，支持整书／卷／章规划、局部编辑、Agent保存与返工、来源提示、历史读取及Markdown／JSON导出。关键转折用有序列表即可；只有作者任务确有需要时再加入拖拽画布。

采用TypeScript、React和esbuild，宿主内部采用Cordis；规划校验、局部修改和导出由受管Node确定性动作提供，数据经现有宿主动作存储。不增加独立数据库、账号、模型循环、支付或同步服务，权限为精确作品的`objects.read`和`objects.write`。正常链路为Codex→河图CLI/MCP→插件，Skills按需指导；界面读取同一成果，无窗口业务必须独立验收。

共用创作方法继续由所选Skills承担，本包维护自己的Schema、动作说明及`CAPABILITIES.md`。无需为每次安装再分发一个Codex插件，也不把专业功能清单长期复制到宿主地图。

## 7. 发布前必须跑通的用例

| 用例 | 通过标准 |
| --- | --- |
| 从空白规划到可审阅卷纲 | 机器保存、GUI阅读和机器回读一致，关闭桌面仍可执行机器操作 |
| 只调整一卷 | 其余卷、正文、设定和正式大纲不因保存规划被改写 |
| 人工编辑与Agent并发 | 旧基线被拒绝，未保存输入保留，无静默覆盖 |
| 保存后丢回执 | 沿原键查到同一成果，不创建重复规划 |
| 结构修改中断 | 单方案不出现半份重排；跨方案独立保存，原操作可接续 |
| 同名卷章、跨作品和撤权 | 使用稳定引用；相同名称不合并，错误对象和失效授权拒绝 |
| 当前对话安装与停用 | 重查后能力出现或消失，旧定位不能绕过停用继续写入 |
| 规划应用为正式大纲 | 单独展示差异和确认，宿主回读成功后才显示已应用；缺少固定来源合同时明确保留缺口 |
| 中文长内容与窄窗口 | 阅读、键盘、输入和恢复可用，不强制画布操作 |
| 停用及卸载 | 规划仍可通用读取及导出，正文和正式大纲保持各自事实 |

插件仓库的README负责入口，`CAPABILITIES.md`维护专业功能与状态，实际包清单负责可执行贡献，测试维护真实通过范围。本篇保留宿主适配与立项取舍，不复制插件完整功能清单。完成验证后按23申请官网目录收录，不提前将设计条目标记为已上架插件。
