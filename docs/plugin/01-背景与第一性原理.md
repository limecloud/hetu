# 背景与第一性原理

## 1. 背景与问题

作者的工作对象是一部持续变化的作品。章节、人物、事件、空间、对白、镜头、素材和作者判断相互关联，任何一次生成都只是其中一次活动。

Markdown 能自由表达长文，JSON 能表达结构与关系，HTML 能组织交互，图片与音视频能呈现感受，Python 等程序能计算和转换。外部 Agent 已经能够组合这些媒介，完成许多原本需要专门软件的任务。因此，河图必须回答：持续使用软件，能比每次临时生成一个页面或脚本多创造什么价值？

另一方面，穷举所有字段、所有关系和所有界面，会形成庞大且难学的软件。一个作者需要卷章规划，另一个需要关系画布，导演可能需要三维调度；让所有人学习全部工具，会把创作复杂度转嫁给人。

目标因此同时包含两部分：提供足够深的创作能力；按当前任务控制作者接触的复杂度。

## 2. 从基本约束逐步推导

| 基本约束 | 直接推论 | 产品要求 |
| --- | --- | --- |
| 创作包含无法预先穷举的表达 | 固定字段和版式只能覆盖部分需求 | 保留自由文档、自定义属性和自由成果 |
| 作品跨越多次生成、修改和工具切换 | 会话中的一次回答不足以承载完整作品 | 保存身份、固定来源、修订和作者决定 |
| 人的注意力与操作学习成本有限 | 功能丰富不能等于入口全部平铺 | 默认任务工作面，深度工具渐进展开 |
| 稳定计算与渲染可由程序重复执行 | 每次重新生成同类程序存在重复成本 | 固化可复用动作、渲染器与交互能力 |
| 创作意图和取舍随作品变化 | 规则不能代替品味与判断 | 外部 Agent 理解意图，作者保留创作决定 |
| 同一作品有多种观察方式 | 视图不能各持一份可写事实 | 一个 Owner、多种投影、共享应用动作 |
| 不同创作者的需求差异很大 | 单一固定工作台难以同时满足 | 按需安装能力，以套件形成默认组合 |

这条推导得到的是可组合创作工作台：持久作品为中心，插件提供专业能力，外部 Agent 执行获权操作，作者阅读、观看、反馈和取舍。

## 3. 生成式 UI 的机会窗口

### 3.1 近期假设

用户提出的切入判断是：实时生成界面可能代表一种未来方向，而当前模型调用仍可能有较高 Token 成本、等待时间和修复成本，因此存在工程化复用的机会窗口。

该判断应写成可验证假设，不能写成所有模型、所有任务都成立的市场事实。简单表单可能适合直接生成；复杂场景、持续编辑和严格版本恢复则可能更适合复用成熟工具。具体分界取决于模型、任务、使用次数、缓存、设备与可接受质量。

### 3.2 总成本模型

```text
任务总成本 = 模型输入输出费用 + 推理与工具等待成本
           + 作者理解和操作成本 + 校对与失败返工成本
           + 开发、维护、适配及分发成本

临时生成路线成本 = 初次生成 + 每次修改与验证 + 持久化和接续成本
复用插件路线成本 = 初次开发及安装 + 每次数据操作 + 后续维护
```

在质量和任务结果相当的前提下，复用次数增加可能摊薄插件的固定成本。反过来，维护频率高、使用很少的能力，可能更适合作为自由成果或模板。不能仅比较一次请求的 Token 数来决定是否插件化。

时间也需分开：首个可见内容时间、可操作时间、完成当前修改的时间，以及作者确认可用的时间。流式出现一个界面，不等于成果已经正确或可以继续编辑。

### 3.3 A2UI 对该假设的修正

A2UI 1.0 的公开设计使用声明式数据、宿主组件目录和原生渲染器，支持组件与数据分别增量更新。它不要求模型为每次交互从零生成完整 HTML，也不要求每次点击都进行模型推理。官方 ADK 适配提供直接处理部分函数请求而不运行 Agent 的机制。详见[02](02-产品与生态调研.md#7-a2ui-与动态表达)。

因此，不能把“动态 UI 必然需要反复生成整套代码”作为成本假设。需要分别测量界面组合推理、目录进入上下文、数据读取与同步、普通程序调用，以及专业渲染本身的成本。Agent SDK 还可以将紧凑推理格式编译为传输消息，传输 JSON 的字节数不能直接当作模型输出 Token 数。

这使实时组合与工程化复用能够共同成立：程序提供稳定的组件和动作，Agent 根据当前任务选择、组合和调整，作者直接阅读与取舍。拖动、排序、筛选、播放及已注册函数可以采用确定性实现；需要重新理解意图和生成内容时再交给外部 Agent。

河图的机会应据此分成两层：近期通过复用、增量更新与专业工具降低任务总成本；长期通过持久作品、创作领域能力、版本与反馈接续形成持续价值。当前模型较慢或较贵，只能支持前一层的部分判断，不能单独证明后一层成立。

### 3.4 动态界面与创作平台的关系

界面协议解决“如何表达和呈现当前交互”，创作平台还需要解决“正在修改哪一部作品、依据哪个修订、执行什么专业动作、哪些结果被作者接受、之后如何继续”。A2UI 可以承载这些能力的界面表达；领域模型、实际组件、动作实现与持久化仍由河图和插件提供。

插件因而既可以交付固定工作面，也可以贡献可组合的创作组件、函数、数据合同和方法。小说规划、人物关系、版本比较和导演预演不必都变成彼此孤立的完整页面。它们可以被外部 Agent 按任务组织，同时保留适合长文编辑、空间操作和媒体播放的专业交互。

接入这一表达协议不要求河图承担理解、规划或生成循环。外部 Agent 提供描述，河图校验并渲染；现有作品操作继续通过共享应用用例执行。

### 3.5 假设的失效条件

当低成本模型、缓存或本地推理显著改善生成体验时，单靠“比生成便宜”建立的优势会收窄。此时应扩大声明式组合和自由成果入口，而不是保护一套过时的固定页面。

河图长期积累的价值还包括可接续作品、专业操作、稳定引用、反馈历史、可比较成果及可交付工程。这些价值应在生成成本下降时依然可用。

## 4. 为什么采用插件化

插件化解决三类已经出现的变化：创作媒介不同、任务所需专业深度不同、能力提供者不同。它让新增能力可以独立制作、安装、升级和退出，也让默认体验保持聚焦。

| 方案 | 适合之处 | 主要代价 | 河图采用方式 |
| --- | --- | --- | --- |
| 所有功能固定在主程序 | 基础能力一致，交付直接 | 主程序膨胀，长尾需求互相干扰 | 保留作品与事务内核、基础阅读编辑 |
| 每次临时生成全部界面 | 针对当前问题表达自由 | 重复构建、状态与修复需要额外处理 | 支持自由成果与临时工具 |
| 只有模板或 Skills | 方法和内容容易分发 | 无法独立提供专业操作与渲染能力 | 作为轻量能力贡献 |
| 创作能力插件 | 复用数据、动作、视图和方法 | 需要合同、兼容、隔离和治理 | 作为专业能力的主要扩展机制 |

插件化不是把每个类拆成插件，也不是要求所有内容先套一个本体模型。只有产生独立使用价值、需要独立变化或能够降低重复成本的能力，才值得建立扩展边界。

## 5. 为什么仍需共享内核

作品身份、修订一致性、授权、事务恢复、采纳与定稿需要统一语义。把这些规则交给可替换插件，会使同一作品在不同工具中产生互不兼容的判断。

内核提供最小且稳定的共同基础；插件拥有自己的专业数据，并通过受管动作引用其他 Owner 的事实。小说正文、剧本对白和制作数据分别归属，不因为同名或同工作区自动合并。

## 6. 从单个工具到创作生态

河图的长期方向是让方法作者、工具开发者、专业创作者和服务提供者都能围绕作品交付能力。小说、剧本、导演预演、资产与审阅可以互相接续，仍保留各自专业表达。

生态成立需要三条循环同时工作：创作者获得可用结果；供给者能够低成本制作和维护能力；作品和反馈能够在能力之间继续流动。安装量本身不能证明这三条循环成立。

本地持有、开放合同和标准导出为生态提供退出路径；推荐、质量验证和兼容维护帮助作者选择。云服务在跨设备、团队协作、托管计算等有明确价值的场景中成立，具体 SaaS 范围需独立验证，不把订阅作为本地作品可访问的前提。

## 7. 需要验证的产品假设

| 假设 | 证据需求 | 反证及应对 |
| --- | --- | --- |
| H01：重复任务使用插件的总成本更低 | 等质量对照，记录模型费、等待、人工和维护 | 低频任务收益不足时转为成果或模板 |
| H02：Agent 操作降低作者学习负担 | 同一任务的完成率、主动操作和求助次数 | 机器入口难用时先改善动作和反馈 |
| H03：持久状态提高跨会话接续质量 | 换会话、换 Agent、插件缺失后的恢复 | 仍需重新解释全书时补上下文与引用合同 |
| H04：第三方能独立完成有效插件 | 从 SDK 到首次通过验收的时间与阻塞 | 依赖内部知识时修正扩展合同 |
| H05：生态能提供持续而非一次性供给 | 被采用、持续维护、跨版本存活和实际留存 | 同质重复过多时改进组合与推荐 |

用户访谈、试点测量和生态数据的执行方法见[15](15-测试验收与追踪矩阵.md)。
