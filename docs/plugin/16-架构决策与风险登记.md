# 架构决策与风险登记

## 1. 决策状态

“既有约束”来自现行产品与仓库规范；“方案选择”是本系列提出的实施建议，需要随原型验证和发布合同继续细化。二者不混写为已经完成的产品能力。

## 2. 架构决策

| 编号 | 决策与状态 | 理由 | 备选和重审条件 |
| --- | --- | --- | --- |
| PADR-001 | 保持外部 Agent 协作，既有约束 | 复用作者选择，河图聚焦作品和工具 | 新增任何内部规划循环需重新定义产品，不由插件隐式引入 |
| PADR-002 | 作者决定与事务留在 Core，既有约束 | 采纳、定稿、授权和恢复需要一致语义 | 专业贡献可提供提案，不可替换最终权限规则 |
| PADR-003 | 能力插件、套件和成果分开，方案选择 | 同时承载复用与特殊表达，减少同质包 | 若用户无法理解分类，改进命名与默认组合，不强迫理解工程层次 |
| PADR-004 | 文件权威、索引可重建，既有约束 | 保留数据持有、Git 和退出路径 | 新权威存储需证明必要性和完整迁移方案 |
| PADR-005 | 正常业务机器入口对等，既有约束 | 降低作者操作负担，支持无窗口工作 | 视觉操控只作界面验收或实际缺少机器入口的外部兜底 |
| PADR-006 | 可执行扩展优先独立工作进程，方案选择 | JS/TS后端不进入Rust内核，Node执行环境与范围单独管理 | 若性能不足，先测序列化与批处理；WASM 等需另证能力与收益 |
| PADR-007 | Web贡献与基础阅读共存，已采纳 | Electron统一渲染，专业能力按需加载 | 按作者确认的Mac UI/UX还原工作台，贡献模型承载扩展 |
| PADR-008 | 固定渲染与动态组合共存，优先验证 A2UI 1.0，方案选择 | 公开协议已支持复用组件、增量更新与确定性函数；专业能力由河图提供 | S0/S1 小原型核对适配，按收益扩大，不整体推翻存储和动作 |
| PADR-009 | 安装、启用、作品使用和工具暴露分开，方案选择 | 降低权限与上下文成本，避免一次安装全量加载 | 可改善展示，但不以合并状态掩盖实际可用性 |
| PADR-010 | 初期允许重启应用更新，方案选择 | 优先可靠合同，控制热更复杂度 | 真实连续任务需要时验证热更、排空和旧合同共存 |
| PADR-011 | 先本地包和静态索引，方案选择 | 支持独立供给和验证，避免先建大型市场 | 有稳定供需、结算和治理能力后评估交易服务 |
| PADR-012 | 不以 Schema 穷举全部创作，方案选择 | 创作开放性与可操作结构需要共存 | 根据真实动作逐步增加有类型结构，保留自由内容 |
| PADR-013 | 卸载不删除作品，既有原则的扩展 | 作者内容生命周期独立于工具许可 | 历史清理另有明确范围、引用影响和恢复流程 |
| PADR-014 | Electron＋TS插件宿主＋Rust Core，已采纳 | JS/TS/React插件；注册交互留在TS，Rust保持作品事务 | 原生仅作对照；依主39的插件、中文、平台及退役门禁验收 |

## 3. 策略风险

| 风险 | 影响 | 触发信号 | 应对 |
| --- | --- | --- | --- |
| 只依赖当前模型慢和贵 | 生成成本下降后价值被压缩 | 临时生成在等质量任务中全面更便宜 | 扩大动态组合，围绕持久作品和专业操作验证价值 |
| 以宏大愿景替代真实需求 | 大量基础设施没有采用 | 用户不能指出插件完成的具体任务 | 回到试点和用例，停止无需求扩展 |
| 插件数量成为目标 | 重复低质供给和选择负担 | 收录增长但采用、维护和接续不增长 | 分开统计，优先套件、去重及场景验证 |
| 模仿全部专业软件 | 团队维护成本失控 | 需求扩展到完整 DCC、NLE 和团队平台 | 提供合同、预演和外部适配，限定交付责任 |
| 本地软件与 SaaS 定位混乱 | 用户不知道内容和费用归属 | 基础创作被要求注册或上传全书 | 保持本地持有；云能力按具体价值独立立项 |

## 4. 工程与生态风险

| 风险 | 影响 | 触发信号 | 应对 |
| --- | --- | --- | --- |
| 插件共存时复制事实 | 正文、对白或场面不一致 | 两个视图保存不同角色或镜头数据 | 明确 Owner、固定引用和共享动作 |
| 把进程分离当安全沙箱 | 作者数据被任意代码读取 | 无 OS 限制却宣传不可信插件安全 | 先限制模式，完成实机隔离验证 |
| 迁移与代码回退混淆 | 旧代码破坏新数据 | 升级后直接降级继续写 | 显式迁移、保留旧修订及只读回退 |
| 无界消息和媒体回传 | 资源耗尽、长等待和 Token 浪费 | 全文与大媒体被重复内联 | 分页、固定引用、有界附件及投影 |
| 生成任务重复提交 | 重复费用或副作用 | 超时后换键、取消后重新生成 | 原计划查询，持久 unknown 和外部任务身份 |
| 第三方开发依赖内部知识 | 生态无法独立成长 | 开发者必须修改 Core 或导入私有模块 | SDK 与第二开发者验证作为阶段门槛 |
| 许可与素材权利不清 | 分发或交付受阻 | 公开源码被误认为可自由商用 | 逐依赖、素材、字体和服务核验 |
| 动态页面修改失去历史 | 反馈和成果不可接续 | HTML 重生成后状态或意见丢失 | 页面、数据、锚点和组件版本分别固定 |
| 引用引发跨对象泄漏 | 同根或关联作品越权 | 凭 ID 或标题读另一端 | WorkRef 和每次实际授权检查 |
| 规范与源码分叉 | 设计动作被当已发布 API | 文档示例不能被实际能力发现 | 发布前同步主规范、contracts 与真实入口 |

## 5. 未决问题及验证责任

| 问题 | 需要什么证据 | 负责的工作 |
| --- | --- | --- |
| 作者愿意接受多大操作深度 | 各人群的真实任务、访谈和观察 | 产品研究，S0与S2 |
| 画布和三维具体引擎 | 性能、许可、无障碍和标准导出原型 | 客户端与插件试点，S3 |
| 目标平台可实现何种沙箱 | 文件、网络、子进程和逃逸实测 | 安全与制品，S3/S4 |
| A2UI 的实际收益及版本选择 | 官方规范固定版本、原生及领域目录适配、等质量对照 | 动态视图，S0/S1原型与S6扩大 |
| 第三方维护窗口如何承诺 | 真实升级成本与开发者反馈 | SDK与生态，S4/S5 |
| 付费能力和团队服务的需求 | 采用、续用、支持和实际协作价值 | 产品与商业研究，供需成立后 |

未决问题不需要阻塞不依赖它的工作。需要具体框架、版本或发布承诺的部分保持待验证，不用看起来合理的配置填补事实。

## 6. 变更治理

外部产品或协议更新先记录来源和适用范围，再判断是否改变本系列的选择。新的性能数字、插件数量、价格和服务状态均绑定采集日期，不变成永久产品承诺。

采纳设计时同步唯一 Owner 文档和追踪矩阵；已发布动作及数据不能直接换语义。实现证据进入现有实施与验收体系，研究快照保留原口径和限制。
