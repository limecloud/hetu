# 河图洛书创作插件体系设计

版本：0.1；日期：2026-11-16；状态：已采纳技术方向的产品与实施设计基线。

本系列研究如何让小说、剧本和视频创作能力按需组合，形成作者与外部 Agent 共同使用的、可持续积累的创作工作环境。河图负责作品、确定性操作、可视化与作者决定；理解、规划和生成由作者选择的外部 Agent 完成。

## 简介

核心主张：河图需要有足够深的创作结构、操作能力和可视化表达，让作者和 Agent 都能围绕整部作品工作。

插件是创作能力的交付单元，可以贡献数据、动作、视图、方法和连接。套件组织多项能力服务具体创作场景；自由成果承载当前作品中的特殊表达。默认体验保持易读易用，需要深度工具的人可以逐步展开。

本系列包含需求和拟议合同，不是插件系统已经上线的声明。已有能力以实际能力发现、`contracts/` 和[实现基线](../20-实施路线与里程碑.md)为准；现有创作工作台的工作包与进度继续由[38](../38-创作工作台重构执行计划.md)维护。

安装启用后的插件通过公开SDK复用核心服务，不另申请插件作品权限。核心分层、兼容及审计见[27](27-开放宿主SDK与核心能力审计.md)；领域与本体语义归[主28](../28-领域设计与边界上下文.md)。

## 边界

- 本系列扩展创作工具的可组合性，不引入河图内置 Agent、聊天或自主生成循环。
- 画布、导演台和多轨界面可以提供深度能力，作者按需使用；正常机器业务不依赖 GUI 点击。
- 插件数量、市场收录数、能安装、能加载、内容质量、实际采用分别衡量。
- 作品文件继续作为权威，首期JSON标题投影可重建，SQLite设计用于后续规模评估；授权与本机安装记录在私密本机存储中单独持有。
- 当前源码中的类名、路径和动作属于实现事实；本系列中的新类型、包字段、路径和动作属于拟议合同，须经过实施与验收才能发布。

## 协作方式

新增需求使用 `PFR`，故事使用 `PUS`，用例使用 `PUC`，验收使用 `PAC`，API 使用 `PAPI`，架构决策使用 `PADR`。编号在对应 Owner 文档定义，通过15追踪，避免与主系列编号混淆。

外部证据索引见02及 [research-sources.json](research-sources.json)。研究结论不能直接替代用户访谈或实际产品测试。采纳到现行产品合同时，按14列出的联动清单同步主规范、机器合同和实施计划，保留原有作品与历史引用。
