# Let the tools grow around your story

By chapter twenty, Qiao knows who Zhou really is. You ask your Agent to reorganize the cast, but it reads notes from chapter eight. The graph is elegant and the explanation plausible. It belongs to a different revision of your story.

A creative tool needs to connect to the right work before it can help. Whether you inspect that work through prose, a relationship graph or a timeline should depend on the question you are asking.

## Give the work a durable foundation

Novels, scripts and videos can begin independently and connect through explicit sources. Whichever tool you open, you need to know what it read, what it changed and which results you actually chose to adopt.

Software can make identity, sources, revisions, permissions and recovery dependable. Those rules should not need to be improvised for every task.

Professional tools vary much more. One author traces secrets across a cast; another inspects twenty years of chronology; another simply needs uninterrupted chapter reading. Packing every specialized interface into a permanent workspace creates a new learning task before the creative task begins.

Hetu keeps the work foundation stable and lets specialized tools join when useful.

[Novel Planner](/en/plugins/novel-planner/) applies that boundary to long-form writing. Review volume goals, themes, conflicts and detailed plots together, with links to characters, places and clues. The Agent organizes the structure while the author reads and edits through a volume list. Formal chapters, manuscripts and story settings reuse host capabilities. Its preview release provides a fixed runtime package and a specific validation scope.

[Director Stage](/en/plugins/director-stage/) applies this approach to space and cameras. An Agent arranges people, props, cameras and keyframes; the author watches actual white-model previs and can ask, “Wait until he reaches the table before cutting to the close-up.” The floor plan, 3D framing and shot dialogue use one scene. “Let her turn only in shot three” becomes local blocking, preserving other shots. Timing estimates and geometric checks flag issues for review against actual previs. The scene, feedback and revisions remain part of the same work. A reusable project and a final image remain separate results.

## A canvas can be optional

Relationships can be a graph. Events can be a timeline. Other questions may call for images, tables or a specialized view. There is no single best representation for every creative problem.

That freedom should not require authors to construct interfaces themselves. Tell your Agent: “Map only the relationships the protagonist currently knows about. Ask me about uncertain connections.” It discovers the available tool, checks scope, reads the permitted material, saves a structure and reads it back.

You inspect the links and ask for changes. Manual editing remains available without becoming a prerequisite. Authors make creative decisions; software and Agents handle operations that can be carried out precisely.

## A new result does not require a newly invented application

Generated interfaces can make complex results easier to understand. Google’s [A2UI](https://github.com/a2ui-project/a2ui) separates an Agent’s interface description from an application’s controlled rendering components; it does not require arbitrary web code for every response.

Latency, model cost and correctness change over time. No interface is inherently the cheapest. For recurring graphs, timelines and review tasks, reusing a tested layout and persistence logic can reduce repeated generation and correction. The Agent can concentrate on the particular story.

This value extends beyond today’s model costs. Stronger models produce more material, increasing the need to connect results to durable sources, revisions and author decisions. Interfaces may become more dynamic while those rules remain essential.

## Workspace plugins and assistant integrations have different jobs

[Hetu creative plugins](/en/plugins/) live in Hetu and contribute views, professional data or actions. Relationships and Story timeline are concrete examples.

Skills and client integration packages live in the external Agent environment, providing methods and a connection. A new Hetu plugin does not need a corresponding Codex plugin. A connected Agent queries current installed and permitted capabilities again; it does not automatically know that a tool has appeared.

Trusted Hetu plugins use public host capabilities once enabled; the external Agent’s work connection remains separate. Graph editing, manuscript adoption and author finalization each follow explicit rules.

## Start an ecosystem with tools that can be checked

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) separates packages, distribution and indexes: npm versions or pinned Git commits carry code, static indexes support discovery and a local manager performs installation. Clear boundaries and low contribution costs are useful lessons. A large catalog alone establishes little about usability.

Hetu uses GitHub for source and listing collaboration, a curated website catalog for discovery and a local manager for installation. Developers use JS or TS, with React for views. Each package maintains its own capability list. Catalog entries point to real sources, versions and permissions. Package validation, runtime compatibility and a completed creative task each need their own evidence.

A useful plugin may solve just one recurring problem. Make it work for one project, then let more authors choose it. Tools can grow without making everyone learn everything.

## Use only what this work needs

Choose tools for a concrete problem in the work. Try an expression in conversation first; add an extension when professional structures, comparisons or delivery need it. Ordinary manuscripts and selected exports should remain retrievable.
