# 插件发布与上架

GitHub 负责源码、版本说明、问题反馈和收录协作；官网插件中心负责发现与介绍；河图本机负责校验、安装和启停。可信插件启用后复用宿主公开 SDK，外部 Agent 的作品连接独立管理。发布源码、被目录收录、实际安装和运行通过，需要分别核验。

## 1. 先完成一个可验证版本

按[开发指南](plugin-development.md)生成完整分发目录并校验。包内维护 `plugin.json`、`CAPABILITIES.md` 和许可，功能说明与实际贡献一致。

给版本写清：解决什么创作问题、支持什么宿主与系统、要求什么权限、有无外部服务费用、已有数据如何读取和迁移。功能、权限或 Schema 改变时发布新版本，不用同一版本替换不同字节。

## 2. 固定源码与制品

源码放在你维护的仓库，版本说明指向确切提交。通过 GitHub Release 等可核验来源提供已经构建的分发文件，记录制品摘要与解压后的包校验摘要；两种摘要分别对应下载文件和实际包内容，不能混用。

运行包包含编译好的界面和必要依赖，不要求普通作者在安装时运行 npm 构建脚本。可以使用 npm 维护开发依赖，但不要把 npm 包发布成功当成河图已支持从 npm 一键安装。

发布前，下载自己的制品、解压到新目录、重新校验，并核对与测试包一致。删除源码中的密钥、真实作品和授权记录。

## 3. 提交目录收录申请

使用 [GitHub 插件收录表单](https://github.com/limecloud/hetu/issues/new?template=plugin-listing.yml)提交申请；持续更新可沿原申请补充，目录修订通过代码审阅管理。

需要准备：插件 ID 与精确版本、源码提交、发行渠道、分发制品地址、双摘要、文件大小、许可、作者与维护渠道、创作场景、双语简介、宿主能力使用说明、宿主及系统兼容证据、安装与实际任务验证。使用真实演示资料并注明对应版本，不上传作者正文。

不必为每个题材换个名字重复上架同一套工具。分类和标签帮助发现，独立插件应具有明确能力或维护边界。

## 4. 审核与展示

维护者分别核对来源、包格式、权限、运行兼容和创作场景。通过哪一层，就说明哪一层；仓库存在和下载量不代表安全、质量或实际可用。

官网维护精选条目，不替用户执行安装。安装仍需核对本次确切包和选择；外部 Agent 的作品连接独立核验。一个河图插件不需要对应一个 Codex 插件。

维护者将外部固定发行信息登记到 `apps/website/src/data/plugin-listings.json`，作者场景写入 `src/lib/plugins.ts`，功能清单链接到插件确切提交。目录构建不执行外部代码；实际下载、解压与包摘要核对须单独记录。[小说规划](/plugins/novel-planner/)提供这类条目的实例。

## 5. 更新、撤回与停止维护

新版本提供变更说明、权限差异、数据迁移和回退边界，重新提交该版本的验证证据。旧版本证据不自动继承；回退程序也不能把旧 Schema 强行写进新数据。

严重问题应及时说明受影响版本并请求撤回目录推荐；保留已有用户的读取和安全导出路径。停止维护时提供源码与数据格式说明，明确维护状态，不静默删除用户数据。

完整开发、发布、审核和治理规范见仓库[插件系列文档](https://github.com/limecloud/hetu/tree/main/docs/plugin)第22～24篇。
